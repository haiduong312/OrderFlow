# ADR-029 — Recoverable checkout, payment and durable live customer views

Date: 2026-11-16. Status: accepted for milestone 21 and the requested notification/realtime UI slice of 23. Extends ADR-015/018/019/020/024/027/028.

## Inspected gaps and scope

Reuse real CreateOrder, owner order list/detail/cancel, payment initiate/attempt GET, notification list/read/count and the existing cookie SignalR hub. The original Customer contract lacked a way to enumerate previous attempts or read capture/refund recovery across reload/devices; Admin audit DTOs are unsuitable for customers. Add only the necessary owner-only GET `/api/orders/{orderId}/payment-status?page=1&pageSize=20`. The simulator has restricted machine/operator API routes and **no customer payment-page/redirect URL contract**. Do not invent a provider UI or expose simulator machine/control/HMAC secrets in a browser. A Development-only explanatory notice directs the operator workflow; provider/reconciliation behavior remains the existing supported Development/Testing simulator. Production builds omit the notice and contain no simulator controls/URLs/secrets.

Pages: protected Customer `/checkout`, `/orders`, `/orders/:id`; authenticated `/notifications`. Existing catalog/cart/auth remain. No checkout/payment write semantics, callback/worker algorithm, inventory coordination, database schema/migration or .NET dependency changes. Add exact stable `@microsoft/signalr` **10.0.11**, verified from npm's stable 10.x line, compatible with the installed .NET 10 hub; preserve the rest of the frontend pins. No JWT, token persistence, UI event-sourced reporting platform, fake checkout/provider success or hosted deployment.

## One durable intention before a POST

Normalize checkout to the exact UTF-8 request JSON `{"items":[{"productId":"canonical-lowercase-uuid","quantity":integer},...]}`: sort UUIDs lexically (equivalent to the backend's N-format order), reject duplicates, 1–100 lines and quantities 1–1000. Do not send the backend's internal hash-format `version` field as an unmapped request field. Generate a UUID key once, synchronously persist body/key, then send that exact stored **string** with `Idempotency-Key`. ApiClient's bodyText path avoids reserializing it. Server CreateOrder normalizes/hash-checks and stores the original 201 bytes; PostgreSQL still protects stock/idempotency. A disabled button/inFlight ref or browser lock cannot authorize/reserve stock.

Storage key `orderflow-operations:v1:<authenticated-user-uuid>` contains version 1, one `{key,body,orderId?}` checkout record and <=20 `{orderId,key,attemptId?}` payment records. Payment initiation's normalized body is always literal `{}` under this version; no prices/totals/name/email/role/token/provider secret or full order/payment DTO is stored. A confirmed ID is only a reference: read the actual owner order/status before presenting its state. Checkout confirmation verifies owner and matching product IDs/quantities against server items. These minimal recoveries are intentionally retained across logout so signing back into the **same user** can safely resume. Another account's app context never loads that key. Same-origin localStorage is not encrypted/XSS-proof account storage; API ownership remains mandatory.

Web Locks serialize operations per origin/user across tabs, re-reading storage **inside** the lock. Without durable writable storage or Web Locks, block mutation rather than falling back to a fresh memory-only identity. Hold the browser lock over the bounded request, never a business DB transaction. Cross-device browsers cannot share this local lock/recovery: server unique keys/state transitions remain the coordination boundary; two independently authorized intentions may legitimately create two orders. No external exactly-once claim.

Parse at most 24 KiB UTF-8, whitelist/validate format/IDs/body/version and bound payment records. Unknown/malformed/unavailable storage fails closed, not a silent empty cart/rekey. If unresolved storage disappears while the instance remains alive, retain its in-memory body/key and block until explicit handling. Completely clearing browser data/reloading after loss cannot magically recover the old key: inspect My orders/support before starting another intention. Explicit Reset writes an empty versioned record so other tabs distinguish an app reset from lost storage. No automatic TTL removes an uncertain intention. Old acknowledged payment references can be pruned to admit another order; unresolved entries cannot be silently pruned.

Transport errors, abort/15-second request timeout, malformed/lost acknowledgement and 5xx leave key/body unchanged. They do not clear cart or generate a new intention. Auth/CSRF/other 4xx errors also retain recovery for deliberate handling, without automatically replaying the POST. The user can **Recover original checkout/payment request**; replay goes to the original body/key even after current cart changes, catalog archival, expiry or payment-state progression. Never use a cart edit to overwrite the old record.

## Resolve, finish or explicitly abandon

A successful CreateOrder acknowledgement adds only orderId to recovery. The checkout screen then GETs owner order detail and verifies immutable items before showing its authoritative total. “View order & finish checkout” explicitly closes the record, clears the shared-device cart **only if its normalized items are still identical**, then navigates to detail. A modified cart remains. A lost response never clears it. Closing a known intention is separate from deciding the order paid.

A changed cart can become a new intention only after resolving/finishing the old one or an explicit checkbox + **Discard checkout recovery**. The warning says this does not cancel an existing order/reservation, recommends My orders and eligible cancellation, and warns that a new intention can create another order. Invalid recovery has similarly acknowledged Reset. Payment initiation replays the same order/key after timeout; acknowledged attempt IDs are read through durable status. Only an explicit “Start a new payment attempt” after a server-reported Failed attempt replaces a resolved key; the server still validates eligibility and reuses any unresolved active attempt. An unresolved payment record can also be explicitly discarded with a separate warning that this does not cancel a charge/refund. No failure path silently clears it.

Old-account success/error side effects are fenced by SessionController.guard before/after network. UI/account context drops in-memory recovery when identity is restoring/changing/unavailable and creates a new scoped instance only for verified `/me`. Cross-tab storage events reload the current scope only. The existing device cart intentionally remains shared under ADR-028; it is not a private order cache.

## Authoritative order, expiry and money

Order list/detail keys include owner and all filters/pages. New private detail/payment/notification keys include userId, entity IDs, page/pageSize/unreadOnly. Immutable line prices/totals come from the server as invariant USD strings and format with existing bigint cents; pending/cart estimates never override them. Cancel UI uses server CanCancel/status, then POSTs with CSRF, displays the actual result/error and refetches. A payment can still capture after cancellation; late compensation is separate.

Countdown uses server `Expiry.ObservedAt` and `ExpiresAt` plus elapsed `performance.now`, not the browser's calendar clock. Equal/past deadline displays zero and waits for normal polling/manual refresh for the next server decision; it does not write Expired, Confirmed, Paid or disable authorization based on a local timer. Network/render/suspension lag means this remains informational. Dates display in the device time zone with a note; persisted timestamps are UTC. No query/redirect/return parameter can confirm payment, and no client follows an invented simulator success URL.

Queued/Pending/Unknown/provider-observed Succeeded remain distinct from a verified merchant Captured/allocated capture and confirmed order. Payment-status read model uses one request-scoped Repeatable Read/READ ONLY transaction, owner existence check, SQL budgets/cancellation, sequential projections and bounded deterministic pages (1–100/page). Each attempt/capture/refund section uses the requested page independently, with total counts. It omits provider request/transaction/capture/refund identities, raw payloads/observations, leases and credentials even from SQL projections. Snapshots from separate order/payment requests may differ briefly; do not treat them as an atomic combined quote.

Capture.Allocated=false visibly means captured funds did not pay this order; order stays Cancelled/Expired. Refund Pending means intention/uncertainty, Succeeded means confirmed returned funds, NeedsReview means unresolved support work. The UI never labels Created/Completed/redirect success as captured money or assumes pending/review refunds succeeded. Existing callback/reconciliation/compensation logic remains authoritative. No customer refund/return command is added.

## SignalR hints and durable catch-up

Opt in at build/dev time with `VITE_ORDERFLOW_REALTIME=true`; backend Realtime must also be explicitly enabled/configured as ADR-024. Default off retains durable HTTP/manual/polling behavior, keeping optional dependencies out of checkout. Vite `/api` proxy enables WebSocket upgrades, preserves same-origin Host/Origin, and keeps normal negotiation. Production proxy affinity/forwarded headers/shared protected keys remain milestone 26.

Official JS client uses WebSockets **with negotiation**, Identity cookies, no accessTokenFactory/query token and no SSE/LongPolling fallback. A custom official HttpClient wrapper obtains the current in-memory CSRF header for each unsafe negotiation, restricts destination to the same-origin hub, preserves status/ProblemDetails and fences user scope. CSRF failure invalidates token state; a later bounded/manual connection attempt retrieves it again. Raw SignalR/network/connection-token logging is disabled. There are no arbitrary client group/subscription methods.

Listen for ConnectionReady and NotificationAvailable. Only three UUID hint identities are accepted; event IDs are deduplicated in a bounded 256-entry set. Hints invalidate matching owner order list/detail/payment and notification/unread queries; never write hinted status, increment unread, or treat a hint as durable delivery. Ready/reconnected invalidates all current-user durable queries, so missed hints are recovered by HTTP. Duplicate hints are harmless. Stop immediately through a synchronous session subscription before login/logout/account switch network actions; stale callbacks are inert. Finite reconnect delays 0/2/10/30 seconds; initial failure/exhaustion becomes Offline with a manual Reconnect action. No endless retry loop.

Order detail/payment poll every 15 seconds while mounted; order list/notification/unread poll every 30 seconds. Manual refresh/focus/session restore also catch up. Polling pauses normally in background, and realtime may be lossy; no instantaneous/continuous-revocation guarantee. Query guards/owner SQL still protect every read. A server intentional Hub.Abort can close without auto-reconnect; actual network loss is the automatic reconnect test, and the user can reconnect a deliberately closed channel.

## Verification / limits

Unit tests exercise exact body/key persistence on network/timeout/503, storage failure/missing/corrupt data, scope isolation, deterministic two-tab lock arrival, explicit abandon/close, payment-key reuse/new failed intent, server-time countdown and hint invalidation/dedup/reconnect/stop. Browser tests use real Kestrel, Vite, Identity/CSRF, PostgreSQL merchant **and independent simulator DB**, real simulator HTTP, production submission/reconciliation/refund iterations and real Redis/WebSockets. A nonce test-only driver advances injected time/steps workers, processes committed events with the production notification consumer and validated dispatcher, and sends duplicate hints; it does not forge successful customer API responses. This harness steps consumer/dispatcher directly; existing RabbitMQ/two-API tests cover broker/backplane plumbing separately.

The test driver never ships in API.Program. Lost create uses route.fetch to commit a real 201 then loses its response. Payment-initiation timeout withholds a committed 202 until the actual client timeout. Reconnect aborts the underlying HTTP connection (not intentional Hub.Abort), gates actual renegotiation, changes durable state while disconnected and releases it for catch-up. Late capture goes through real provider lookup settlement; rejected refunds produce NeedsReview. Final commands/results/browser scope live in [status](../implementation-status.md) and [frontend runbook](../frontend.md). No fake production default credentials, real external payment/provider, deployed affinity/TLS, production load/browser privacy guarantee or full WCAG audit is claimed.
