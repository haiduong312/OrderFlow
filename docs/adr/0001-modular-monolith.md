# ADR-001: Modular monolith with feature folders

Date: 2026-10-30. Status: Accepted.

## Context

The portfolio needs clear modules and a separately runnable worker, while checkout and payment confirmation must atomically coordinate stock and orders. Distributed services or a project per abstraction would obscure the core behavior.

## Decision

Use three production .NET projects: API, Worker, and Application. Group Identity, Catalog, Inventory, Ordering, Payments, Notifications, and Reporting by feature folders inside Application. API/Worker are composition hosts using the same application services. Controllers stay thin. Use narrow concrete services/interfaces where an actual boundary exists, without a generic repository, mediator framework, or speculative shared kernel.

Use one PostgreSQL database with owner schemas, one scoped Identity-compatible OrderFlowDbContext, and one migration chain. Owner module services alone mutate their tables. Application use cases can call several module services inside one context/transaction. Cross-schema FKs protect core references. Reporting/notifications depend on durable events and do not participate in checkout decisions.

## Alternatives and consequences

Microservices would require distributed coordination without adding portfolio value. Separate module projects/contexts could enforce stronger compile-time boundaries but complicate the required atomic writes. Feature folders make boundaries a review convention; module ownership must be maintained deliberately. A shared schema release and database availability couple hosts. This is intentional for v1; splitting services is deferred.

## Verification

Check the planned layout and schema table in [architecture](../architecture.md), independent API/worker startup, and PostgreSQL integration tests demonstrating cross-module rollback. No application projects are generated by this ADR milestone.
