# ADR-020: Durable compensation delivery and payment lookup settlement

Date: 2026-11-11. Status: Accepted. Extends ADR-003/005/018/019. Completes the requested late-capture recovery workflow, not general customer refunds/returns or a generic outbox dispatcher.

## Decisions

### One settlement path, two evidence sources

Extract PaymentSettlement from the callback processor. Both signed callbacks and authenticated IPaymentGateway lookups use its exact identity/shape, stored order/attempt/key/transaction, currency, positive amount, capture deduplication, eligibility, consumption/expiry/release and full-compensation logic. The caller holds Order first, samples DecisionAt, locks provider transaction/capture identities then the attempt. Reconciliation locks the order/attempt from the persisted claim, never provider-returned IDs. A mismatched lookup is retained in LastObservation and flagged NeedsAttention without allocating stock. A known USD capture with wrong amount still records actual captured money and creates full compensation.

PaymentCapture.Source is Callback or ProviderLookup. For callbacks, retain ProviderEventId/ProviderOccurredAt and the authenticated receipt FK. The current gateway lookup contract does not return either; lookup captures have null event/occurrence and their own local RecordedAt, rather than inventing a signed event or provider time. First capture evidence is immutable; a later callback for that capture remains its own receipt without changing allocation or creating another refund. This extends ADR-019's callback-only evidence shape and permits verified lookup settlement; submit/lookup observations alone still do not bypass the shared business validation/transaction.

### Payment reconciliation

PaymentReconciliationIteration has three phases in independent scoped contexts: claim+commit, provider lookup outside all merchant transactions, order-first settlement+acknowledgement. It shares the existing PaymentAttempt lease token, 60-second lease and eight-delivery counter with submission, preventing simultaneous ownership by the submission/reconciliation loops. Eligible work is previously delivered Queued (crash recovery), Pending or Unknown, including settlement_pending and gateway_response_mismatch observations that need validated settlement. Manual attention codes and exhausted work are not silently replayed. Existing PaymentProcessing may still recover an absent submission under its original provider key; the new lookup-only consumer never submits a new payment.

A matching lease token is required after the order lock and before effects. Callback or newer worker clears/replaces it, fencing old Pending/Failed/success results. Matching Pending schedules backoff; definitive matching Failed ends that attempt and allows normal eligible replacement; Succeeded goes through PaymentSettlement atomically with capture/refund/order/stock/history/outbox and lease completion. Missing lookup is uncertainty, not failure; back off without resubmission until review. Protocol/reference/currency mismatch or permanent authentication/request rejection needs review immediately. Backoff after claimed delivery n is 5,15,30,60,120,300,600,600 seconds; eight committed deliveries maximum including submission, with exhaustion stored at the final claim too so a crash cannot hide it. NeedsAttention plus LastErrorCode is the existing durable manual-review state; no unbounded retries or new client success endpoint.

### Refund execution

Refund identity remains (Provider,ProviderCaptureId,FullCompensation), local CaptureId and stable ProviderRefundKey. Never regenerate it on timeout/restart. PaymentRefund owns Pending/Succeeded/NeedsReview, DeliveryCount, UpdatedAt, NextAttemptAt, lease token/deadline, ProviderRefundId, SucceededAt and sanitized LastErrorCode. Pending includes uncertain delivery; this latest requested three-state model supersedes the earlier planned separate Unknown/Failed refund states. NeedsReview means unresolved/blocked, not proof that money was not refunded. The prior RefundPending intention becomes Pending through a data-preserving forward migration.

Claim exactly one due Pending refund using ordered FOR UPDATE SKIP LOCKED, increment the counter and issue a fresh 60-second token, commit/dispose before I/O. Always LookupRefund by the original key first; only absent result permits Refund using the same immutable key/capture/amount/currency. Simulator refunds are synchronous durable success results; timeout/non-success is not success. Validate response request key, capture, amount/currency and refund ID. Lock the refund in a fresh transaction, check token and terminal state, then save the observation and refund-succeeded outbox atomically. EF's lease concurrency predicate and SQL guards reinforce transitions. Stale token cannot acknowledge another claim. A token may finish after lease expiry if no newer owner reclaimed it; expiry alone never grants an old owner authority over a changed token.

Retry only classified transport uncertainty/HTTP 408,429,5xx, with the same backoff and eight-delivery budget. Other HTTP rejections or identity/money mismatch go to NeedsReview. The eighth claim itself records review before calling HTTP, but that current token can still acknowledge a valid success; a crash leaves explicit attention. Terminal success and manual-review rows cannot automatically regress, and immutable identity/amount/key columns remain guarded. SQL uniqueness protects one local intention/capture and one provider refund ID. Unknown SQL/application failures propagate visibly; known contention postpones a bounded worker pass without pretending a network effect was undone.

### Workers and provider contract

RefundProcessing and PaymentReconciliation are separately opt-in, 20 sequential work items/pass, five-second TimeProvider-aware cancellable polling. Their iterations create a fresh scope per database phase; no shared concurrent DbContext. Both use the existing gateway and restricted Development/Testing loopback simulator configuration; seed commands suppress loops. HTTP timeout is 15 seconds per operation, no automatic redirects/retries; refund lookup+submission normally fit within the 60-second lease. Shutdown propagates cancellation, leaves a durable claim and recovers by the same key after expiry. No refund path touches order/inventory or creates a customer refund/return route.

The simulator/provider behavior required for safe external recovery is explicit:

1. The merchant provider key is durably bound to immutable request facts in the merchant account. Same key/body returns the same transaction/refund identity; a changed body conflicts.
2. Full refund is serialized by capture and key, with unique capture/key/refund identities, so a different key cannot issue a second full refund for that capture. Capture/amount/currency must match previously captured provider funds.
3. Commit capture/refund success before acknowledging HTTP; lookup by original key must recover that durable result after response loss/restart. IDs and success never regress; retention must exceed all retries/recovery (v1 retains them indefinitely).
4. Map only a definitive provider failure to Failed. A provisional failure is Unknown. The simulator's operator-only Failed->Succeeded fault scenario needs a later verified callback to override a completed Failed attempt; failed attempts are not polled forever. If a real provider cannot guarantee definitive failure, reliable notifications or audited same-identity reconciliation is required.
5. Provider capture occurrence is separate from merchant allocation time. A successful capture discovered after expiry is compensated, never used to resurrect an order.

Simulator refund scenarios are durable/operator-only: Succeeded, TimeoutBeforeAccept, TimeoutAfterSuccess (commit then withhold HTTP until cancellation), and Rejected (422 without an effect). Scenario controls cannot rewrite an existing effect; provider refunds survive host restart in its independent database. Local leases/transactions do not create an external exactly-once guarantee: safety depends on these provider idempotency/capture/lookup/retention contracts. Tests prove one effective refund under the simulator's contract only.

## Verification / limits

Actual PostgreSQL + independent simulator HTTP tests cover response loss after success, provider restart, local acknowledgement failure after provider commit, concurrent claims at the actual pre-claim SQL boundary, stale-lease fencing, no merchant transaction over lookup/refund, callback versus lookup at the shared order lock, missing/pending/failed/mismatched lookup, exact expiry, repeated late-capture callbacks, bounded review states and shutdown after external effect. A populated legacy migration test preserves original refund key/amount/capture and initializes due metadata; Down refuses evidence loss. No arbitrary sleeps prove races.

No real money/provider claim, generic dispatch, automatic simulator callback delivery, audited operator-retry UI/command, customer refunds/returns or deployment hardening is added. Exhausted/refused/mismatched outcomes remain visible for manual investigation using the original identity; never repair them by creating an unrelated refund.
