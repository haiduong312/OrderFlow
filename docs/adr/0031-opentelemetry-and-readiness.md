# ADR-031: Optional OpenTelemetry, durable context and intentional readiness

- Status: Accepted
- Date: 2026-11-17
- Scope: requested observability slice of milestone 28 and readiness prerequisite of 25

## Decision and supported versions

Instrument the existing API and Worker, without introducing another service abstraction, event platform, schema migration or correctness dependency. Pin the actual stable OpenTelemetry.Extensions.Hosting, Exporter.OpenTelemetryProtocol, Instrumentation.Http and Instrumentation.AspNetCore **1.21.0**, verified against the official NuGet feed on 2026-11-16. Add standard Microsoft.Extensions.Logging.Console **10.0.14**, matching the repository's existing Hosting line, for a shared safe console formatter. Preserve SDK10.0.115, EF10.0.14, Npgsql10.0.0 and existing business dependencies; update all six NuGet locks.

Use stable Npgsql's built-in `Npgsql` ActivitySource for EF-generated and explicit PostgreSQL commands rather than introducing a preview EF instrumentation package or recording the same command twice. Npgsql's documentation labels its semantic convention support experimental; the installed driver API/source is verified and no preview package is installed. Tracing follows the actual database command, not every in-memory LINQ operation. HTTP uses supported ASP.NET Core and HttpClient instrumentation. Do not enable HTTP request/response body/header capture or sensitive EF logging.

## Meaningful operations and durable lineage

Custom activities are limited to `checkout.create`, `outbox.publish`, `notifications.handle`, `realtime.dispatch`, `reservations.expire` and `email.deliver`. No custom span is created for an empty poll. Publication starts after the claim transaction has closed; external I/O retains its existing transaction boundary. Notification handling spans the transactional inbox/effect/child-outbox commit, while ACK transport failure is a separate classified log/counter. Uncompleted operations set Error and allow exceptions to propagate. IDs are trace/log attributes only.

OutboxMessage already captures W3C producer context at insertion, and EventEnvelope/AMQP headers already carry it alongside immutable correlation/causation IDs. Keep those original bytes/IDs unchanged across publication attempts. Publish and consume spans are therefore sibling children of the durable producer span, not a newly rewritten publish-attempt context. They share its trace ID even when the original HTTP execution context is gone. A new notification-created event records the consumer's own context when sampled; without an activity it preserves the incoming durable context. Legacy envelopes without trace context start independent roots with correlation IDs, not an unrelated ambient activity. Redelivery creates another span for the same event and does not imply another business effect.

W3C context is diagnostic, never authorization/idempotency. Set the default text-map propagator to trace context only; do not forward arbitrary inbound baggage to dependencies. Parent-based ratio sampling defaults to1 for this local portfolio demo and remains configurable0–1. Unsampled/legacy/missing telemetry and late independent payment evidence can leave partial trace trees; durable order/event/audit identity is still required for investigation. No exactly-once tracing/delivery claim.

## Redaction and bounded metrics

Run TraceRedaction before batching. Only explicit method/status/route/protocol/DB-operation/error-type/messaging-system/event/correlation tags survive. Remove SQL, parameters, database/host names, paths/URLs/query, user agents, arbitrary enrichment and exported tracestate. Replace dependency span display names with safe constants. Do not opt into automatic HTTP exception capture. Npgsql10 calls `Activity.AddException`; the supported .NET10 ActivityListener.ExceptionRecorder replaces message/stack tags before default recording, retaining only exception type. Status descriptions are cleared too. Tests inject an actual PostgreSQL exception marker and inspect exported spans for absence.

Both standard Console and OTLP ILogger use a whitelist of structured fields, event name/number, trace/span IDs and exception type. Never format arbitrary message strings/exception objects, scopes, OriginalFormat, provider payloads, body/recipient, tokens/cookies/CSRF, connection strings or SQL. Unknown fields are omitted; values/counts are bounded. This intentionally trades raw framework text/stack diagnostics for safe operation codes/types. A full trace remains useful without SQL or secrets. This controls the application's registered providers/exporters, not arbitrary third-party agents or an operator deliberately changing code/configuration.

Metrics use only fixed outcome, component, failure-kind and dependency labels; no order/user/product/event/key/route/queue/exception-message labels. SDK per-instrument cardinality limit is100 regular combinations plus one SDK overflow point; checkout's explicit histogram drops unexpected tag keys and permits8 regular combinations plus overflow for four fixed outcomes. Resources identify static API/Worker services, not business entities. Event IDs and trace IDs may appear in logs/traces, never metric labels.

Checkout HTTP duration/counter cover POST `/api/orders`, including authentication/CSRF/validation rejection, replay, server failures and cancellation. `success`, `rejected` (4xx), `server_error` (5xx), `cancelled` are distinct. Business service activity is narrower than the whole HTTP histogram. Processing failure counts are attempts, not unique failed business events; duplicate/redelivery failures can count again. Expiry completion lag records only after commit, from ExpiresAt to locked decision time, while outstanding expiry lag is a separate gauge.

An opt-in hosted sampler uses independent scoped contexts, sequential SQL aggregates, 2s command and5s total sampling budgets, every15s by default (5–300s configurable). Sample outbox Pending+InFlight count/oldest OccurredAt age and Failed count, due PendingPayment orders/oldest expiry lag, and Pending/NeedsReview refunds separately. Filter settled/published history from the aggregates. There is no SQL/network I/O in observable callbacks or checkout's critical path. A failed sample preserves its last values, sets success=0 and exposes increasing snapshot age. Initial missing data remains missing, not a fabricated zero. These are approximate observations from separate statements, not a transactional reporting snapshot or proof that a worker is progressing. Count scans remain bounded by deadlines, not constant time; do not add speculative indexes here.

## Liveness and readiness

API `/api/health/live` checks only process HTTP responsiveness. `/api/health/ready` returns200/Healthy only when PostgreSQL connectivity and this binary's migration history are ready, otherwise503/Unhealthy with no-store and no sensitive detail. No auto-migration/DDL. It does not verify every table/privilege/capacity invariant or guarantee checkout success after the probe.

RabbitMQ, Redis, SMTP, the gateway and OTLP are not API admission dependencies: the existing transactional outbox can buffer committed work while the API continues checkout. Buffering is not unlimited storage or a production capacity guarantee; backlog/age/failure alerts must accompany this policy. Public cache/live hints remain optional.

Worker internal readiness is available through `check-readiness` (exit0/1 plus safe JSON) and telemetry dependency/runtime gauges. It requires PostgreSQL/schema, RabbitMQ connectivity when publisher/notification consumers are enabled, and SMTP TCP reachability when email sending is enabled. Disabled jobs add no dependency. Broker connection readiness does not assert topology/subscription health; SMTP reachability does not prove acceptance/delivery. Gateway/OTLP are excluded and pending/refund/error data exposes unresolved work. A worker can be unready while its process is alive; existing finite retry/fatal-host behavior remains unchanged, not silently healed or hidden. No public worker HTTP listener is added.

## Optional local profile and verification

Standalone `compose.telemetry.yaml` avoids requiring the main Compose DB secret for telemetry-only startup. Pin **grafana/otel-lgtm:0.41.0** and its verified manifest digest. It bundles OTLP Collector, Prometheus, Tempo, Loki and Grafana. Bind only loopback3000/4318, provision a read-only application dashboard with Viewer access and bound container resources. No application/DB depends_on telemetry. This is a development/demo backend, not a production monitoring deployment.

Telemetry and OTLP export are separate opt-ins, both off by default. Bounded async batches1024/128, 1s scheduling, 2s export timeout and10s metric export keep unavailable collectors out of business transactions/startup. Queues can drop data; collectors/viewers are not an audit store. Examples such as checkout5xx >1%/5m with enough traffic, outbox age>60s/5m, expiry lag>30s/5m, Failed/NeedsReview>0, or stale sampling are investigation hints, not production SLOs/guarantees.

Tests cover safe exporters/logs/metrics and actual PostgreSQL/RabbitMQ propagation/backlog/recovery/expiry/refunds/readiness. Optional local-profile verification additionally queries actual Prometheus, Tempo and Loki; it is explicitly configured, not a missing-prerequisite success skip. Core tests do not require LGTM. See [runbook](../observability.md) and exact [status](../implementation-status.md).
