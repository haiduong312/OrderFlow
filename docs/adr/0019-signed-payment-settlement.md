# ADR-019: Authenticated receipts and database-atomic capture settlement

Date: 2026-11-11. Status: Accepted. Extends ADR-003/005/018. Delivers roadmap 17 and confirmation/compensation-intention slice of 18. Refund submission/reconciliation remains deferred.

Extended by [ADR-020](0020-refund-execution-and-payment-reconciliation.md): refund execution and authenticated lookup now use the shared settlement path; callback signature/receipt guarantees remain unchanged.

## Decision

Expose only POST `/api/payments/simulator/callback`, with explicit browser antiforgery exemption because dedicated provider HMAC authenticates it. Enable receipt explicitly with PaymentCallbacks:Enabled and inject a 32–512 character Secret plus KeyId, matching the simulator signing credential. The signing input remains the exact ASCII delivery timestamp, `.` and unmodified request body bytes. Require one key/timestamp/signature header, canonical nonnegative Unix seconds, a 32-byte hex HMAC-SHA256 and at most five minutes skew using TimeProvider; exact boundary is allowed. Use fixed-time comparison. Bound unknown-length as well as declared-length bodies to 64 KiB before authentication/deserialization, reject encoded bodies, missing/duplicate/unknown JSON properties and unsupported schema/state shapes. Cookies/roles cannot authorize this route. No signing material or payload is logged.

Store PaymentEvents uniquely by (Provider,ProviderEventId), preserving exact authenticated bytes/hash and separate provider OccurredAt / merchant ReceivedAt. INSERT ON CONFLICT DO NOTHING arbitrates concurrent receipt; compare raw bytes and hash on a duplicate, 202 for exact replay, 409 plus structured alert for changed bytes. Insert the existing messaging ProcessedMessages inbox in the same transaction before 202. PaymentEvents is the durable external receipt; the generic inbox owns processing status/retry metadata. Unknown references are accepted durably then quarantined, never attached by guesswork.

Settlement is database-only, one fresh DI scope/DbContext and short transaction per event. Discover a due inbox without locks, then lock its referenced Order first and sample normalized UTC DecisionAt immediately after that lock. Provider occurrence and HTTP receipt time are evidence, not allocation authority. Preserve DecisionAt across later waits. Next acquire PostgreSQL advisory identity locks for provider transaction then capture, lock the attempt, receipt and inbox, recheck disposition, validate immutable identities and server amount/currency. Advisory locks serialize provider identity binding across unrelated orders; row/unique constraints remain the database backstop. No transaction acquires another order/catalog lock after payment/inventory locks.

No lease is necessary for this consumer: it holds its inbox row and all effects in one PostgreSQL transaction and performs no network I/O. Another worker can discover the same event but must recheck after its locks; a crash rolls back both effects and completion. This intentionally does not implement the general network outbox dispatcher. Twenty sequential events/pass and a cancellable five-second poll bound work. Only classified PostgreSQL contention is retried: durable five-second scheduling, maximum eight failed deliveries, then Failed inbox with sanitized error; unknown failures propagate and stop Generic Host visibly. No indefinite immediate retries or fake success.

A known exact USD capture can allocate only while Order is PendingPayment and DecisionAt < ExpiresAt. Consume every matching Active reservation in sorted product order (OnHand and Reserved both decrease), confirm once with System history, record immutable PaymentCapture and Captured attempt, append payment/order outbox, and complete inbox atomically. Prior submit/lookup success is merely observation; callback clears its submission lease so an old response cannot overwrite capture/failure facts. Failed may become Captured; Pending/failure cannot regress Captured or a definitive failure. Initiation reuses only Queued/Pending/Unknown, permitting replacement after a mismatched captured attempt when its order remains eligible.

Known positive USD capture with a different amount is still financial evidence: record the actual amount, do not allocate, create full compensation. Expired/cancelled/already-paid/surplus captures each get one RefundPending intention with independent stable refund key. Overdue pending orders expire/release in the same transaction, even for a new event referencing an already known mismatched capture. Existing expired reservations are inspected and only Active ones release; Released remains unchanged. Never resurrect a terminal order or release Consumed inventory. Unknown/mismatched attempt/order/key/transaction/capture or unsupported currency is quarantined with authenticated evidence and operational error, without inventing a refund association.

PaymentCaptures are unique by provider capture and by allocated order; Refunds are unique by provider/capture/FullCompensation and refund key. SQL immutable/terminal guards protect receipts, captures, intentions and reservation disposition. Deferred constraint triggers require an allocated capture to belong to the captured attempt and matching confirmed order, or a nonallocated capture to have a matching full refund intention at commit. A refund cannot refer to an allocated capture. These reinforce transaction orchestration without attempting a cross-table CHECK or an exactly-once external-side-effect guarantee.

## Verification and limits

Actual PostgreSQL tests cover forged/raw-byte/stale signatures, bounds/schema, concurrent receipt deduplication, conflicting event identity, quarantine, authoritative amount, exact expiry boundaries, failure/success reordering, two settlement contexts, cancellation/expiry races before the shared order lock, lock-wait eligibility and frozen decision time, callback/submission-response fencing, executed-SQL/outbox rollback, receipt/inbox rollback, deferred guards, failed replacement and surplus compensation. Tests reconcile balances, terminal reservations, ledger, captures and refunds with fresh contexts and no arbitrary sleeps.

The simulator still generates but does not automatically deliver callbacks. Receipt and settlement are opt-in; absent worker configuration leaves a visible durable backlog. Refund HTTP delivery/reconciliation/operator replay, general outbox dispatch, UI and production readiness remain future work. Migration is additive and refuses a destructive Down; no developer database is migrated automatically.
