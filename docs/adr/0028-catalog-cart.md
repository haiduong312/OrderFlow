# ADR-028 — Customer browsing and a browser-local cart

Date: 2026-11-16. Status: accepted for milestone 20. Extends ADR-027; no change to checkout/reservation authority.

## Scope and query lifetime

Reuse the pinned React/Vite/TanStack Query/Zustand stack and existing public GET APIs. Add `/products`, `/products/:id`, `/cart`; keep existing auth/account/orders routes. No package, production backend, database migration, write API or checkout submission is added. Actual checkout/recovery UI remains milestone 21. The cart review is an estimate check, never a successful order or reservation.

Product list keys are `['public','products',{q,categoryId,page,pageSize,sort}]`; category keys are `['public','categories',{q,page,pageSize,sort}]`; detail keys are `['public','product',canonicalId]`. These public APIs do not vary by identity. Every server parameter is in its key and URL. Query functions forward the provided AbortSignal through the existing status/ProblemDetails fetch client. No server DTOs go into Zustand and no query cache is persisted.

The URL is the browsing state, including pagination/sort/filter history. Normalize invalid values to explicit defaults, bound keyword to 100 characters and page size to 12/24/48, and respect the backend's int offset bound. Debounce keyword changes by 300ms; explicit form submit also works. Changing keyword/category/sort/page size resets page to one. Category choices themselves paginate in groups of 20 so the first response is not mistaken for the whole category collection.

Use the server's existing deterministic sorts (each ends in UUID). This makes offset pages deterministic for an unchanged data set; concurrent inserts/archives/price edits can move rows between requests, and count/page are not a shared cross-request snapshot. Do not introduce client sorting, cursor guarantees or an unrelated backend redesign. No previous-page/filter placeholder is used: a new key shows loading and no old rows. Background refresh of the same key has an explicit fetching message. Lists use the existing 30s staleTime; refresh/revisit/filter actions can retrieve again.

## Cart shape, limits and persistence

Zustand owns immutable cart actions only: add/merge, replace quantity, remove and clear. Product IDs must be nonempty UUIDs, canonicalized lowercase. Quantity is an integer 1–1000 and there are at most 100 distinct lines, matching the existing checkout input limits. Reject invalid actions/overflow without partial changes or silent clamping; removal is explicit, not quantity zero. Text input rejects decimal, exponent, negative, blank and out-of-range quantities with accessible inline errors. A selected quantity is allowed to exceed currently observed availability so intent is not silently rewritten; the cart reports the shortage and withholds a successful review. No optimistic stock mutation occurs.

Persist key `orderflow-cart`, version **1**, shape `{state:{items:[{productId,quantity}]},version:1}`. No names, prices, availability, totals, identity, auth or review result is persisted. Read at most 16 KiB of JSON and inspect at most the first 100 rows; validate shape/quantity/ID, discard unknown fields/invalid rows, and retain the first valid occurrence of duplicate IDs. v1 is the first released format. There is no supported legacy conversion: older/future version numbers reset to an empty v1 cart. Missing/unversioned data is ignored. Corrupt JSON or denied/full storage warns with a constant safe log message and shows a persistence notice; in-memory actions keep working. Oversized data is ignored rather than parsed. A subsequent valid action writes only the whitelisted shape.

This is deliberately a **shared-device cart**, not account-specific private server data. It survives login/logout/account switch and is visibly labeled on the cart page. Auth cookies/private order caches still follow ADR-027's purge/fence rules. Users on shared devices can explicitly Clear cart. Same-origin tabs rehydrate on storage changes/removal; last persisted write wins, with no merge/transaction guarantee for simultaneous tab edits. There is no cross-device sync or account cart API. This policy is tested rather than silently transferring purported account-owned data.

## Estimated money, unavailable rows and review

Only TanStack Query supplies product DTOs. On cart/detail mount fetch each selected product again (`staleTime=0`, always refetch on mount; focus/reconnect also recheck). The hard 100-line bound limits fan-out, but a full cart still costs up to 100 detail GETs; a future measured batch endpoint can improve this if needed. Requests use separate HTTP scoped DbContexts, not a concurrently shared EF context. Successful product responses validate USD string prices and product identity before caching.

Derive line/total amounts with bigint cents and the existing numeric(18,2) bounds. Never convert money to Number, persist totals, trust localStorage price fields, round an overflow or substitute a missing price with zero. Display a full estimate only when every row has a successful product read. A 404 means unavailable/archived/deleted-to-public; retain its ID/quantity so it can be removed. Network/500 errors remain retryable errors, not a fake 404/empty result. Out-of-stock/insufficient Available is advisory and visibly blocks a successful review. Amount overflow has an explicit message and also blocks review.

“Check prices & availability” refetches every selected detail rather than accepting an unexpired browser cache. Compare the previous in-memory displayed prices with the responses and announce any changes; totals use the returned prices. Bind successful review to product ID/quantity/price/version/availability and suppress it while fetching or after edits/errors/shortages. Fence late review responses after cart changes/unmount. Removing an unavailable row and retrying is explicit. No response is manufactured and no order POST occurs in this milestone.

This is **not an atomic quote**. With optional ADR-025 Redis caching enabled, newly fetched catalog fields can still be up to 30 seconds old at lookup; Available is read separately from PostgreSQL. With caching disabled, detail is a normal DB read. Displayed estimates may age further until the next focus/review/refetch; there is no continuous freshness guarantee. Mutation invalidation has the existing refill/failure race. After any check, another customer can reserve stock or Admin can edit a price. Existing CreateOrder validates active category/product, immutable order-item prices and live available stock under PostgreSQL locks and returns authoritative totals; future checkout UI must use that result and its error contract. A cart addition/review cannot reserve stock or promise a price.

## Verification and references

Unit tests use the real QueryClient for parameter forwarding/cancellation, plus immutable cart actions, persistence bounds/shape/version/reset/errors, exact totals/overflow and availability rules. Browser tests run the real Vite proxy/Kestrel/Identity/PostgreSQL harness. Admin HTTP updates/archives products while a real cart is open; UI rechecks show changed prices/unavailable rows and no fabricated success. Auth, storage synchronization, reload, responsive controls, loading/empty/error and deterministic paging are exercised.
