# ADR-034: Bounded disposable failure and load lab

Status: accepted, 2026-11-17. Scope: the requested correctness-under-failure/load milestone; no production changes or public deployment.

## Explicit target and criteria

Use the existing replicated deployment images and an additive local resource/logging/pg_stat_statements overlay. Pin published stable k6 2.4.0 by registry digest in `infra/load/scenarios.json`. That file records criteria **before** provisioning: 1,000 reads at four VUs, eight synthetic customers, four last units, eight duplicate requests, zero unexpected/infrastructure errors, read p95 below a diagnostic 2,000 ms ceiling, zero stock/money/dedup violations, nine required fault cases, and broker recovery within 60 seconds. These ceilings are local acceptance criteria, not production SLOs.

Provision only fresh ignored `.local` inputs and UUID-named Compose projects, random passwords, `.invalid` accounts, localhost TLS port18446 and fixed private subnet172.29.244/24. Refuse remote Docker contexts/DOCKER_HOST, changed criteria, noncanonical fixture IDs/foreign accounts and a populated database at initial setup. Require the project label, database run marker and an internal-only backend bridge before observations/disruptions. No arbitrary target URL, connection string, SQL argument, event executor or production failpoint endpoint exists. The API images run normal Production configuration; all failpoint code is confined to the separate test assembly/Development or Testing simulator hosts.

The k6 container joins only the internal bridge, overrides localhost to the test proxy, validates the generated local CA, follows no redirects and disables usage reports. It receives only its fixture, public CA, script and output bind. It has no host environment, Docker socket, cloud token or public network. Four read VUs/eight write VUs, fixed iterations, 5s request timeout, 30s setup/scenario limits plus5s grace, and a75s subprocess deadline bound execution. No saturation/stress escalation is automatic. Restore/build/test also have finite runner deadlines. Cleanup uses only the recorded project and never deletes volumes.

## Two complementary lanes

1. k6 measures real TLS requests through nginx to two API processes. Read90% product detail/10% category detail; products require a fresh database availability read even when catalog DTOs hit Redis. Eight distinct customers contend for four units; eight parallel same-key requests must return identical stored bytes/one order and observe both APIs. Stop only this project's broker, require checkout readiness and eight successful durable orders, then measure pending/oldest age and recovery to pending0/failed0. SQL observations verify balances against active reservations and movement sums, immutable line totals and checkout uniqueness.
2. A focused .NET runner reuses nine deterministic production-service tests with real PostgreSQL/RabbitMQ/provider HTTP and fresh databases. Actual participant rendezvous, lease tokens, controlled ACK exceptions, channel restarts, SQL completion failures and logical time prove callback/expiry allocation, commit-before-ACK redelivery/deduplication, refund timeout after provider success, concurrent claims, stale outbox/refund owners and confirm-before-SQL-ack duplicates. No sleeps prove race arrival. The HTTP bursts are load observations; the deterministic service tests prove the precise interleavings. ACK exceptions/channel disposal and SQL/TCS gates **simulate** process loss; OS kill at the exact commit boundary remains unmeasured.

The second lane serializes fixture collections and caps selection at nine cases/240s test deadline; small per-case fixture data never shares shop inventory. Its Testcontainers have existing pinned images but no explicit CPU/memory caps, recorded as such. API/worker instances in that lane are independently scoped in-process services, not additional deployment replicas. Do not label their wall-time Stopwatch samples as HTTP p50/p95/p99 or throughput. Business-clock advances900s at expiry and5/60s at retry/lease boundaries are separate from measured wall time.

## Cache conditions and optimization

Cache off/on compares the same request mix and fixed dataset. Clear only the13 fixture catalog keys before a cold probe or a new warmup; never FLUSHDB or delete backplane/private entries. Prime40 reads over12 products/one category. A warm measured run must have zero `pg_stat_statements` catalog DTO queries; separately sourced availability SQL remains. A warmup hit alone does not renew the absolute30s TTL. No L1 or checkout-decision caching is introduced.

An observed .25-CPU worker allocation throttled its existing readiness CLI and caused2s DB probe timeouts while the worker main process queried successfully. Raise only the load overlay's worker cap to1CPU and rerun readiness; keep application timeouts/readiness semantics intact. Save before/after cgroup/probe evidence. A separate experiment reduces only EF command log verbosity after observing roughly900 command events per1,000 cached reads, then reruns the same mix. It may reduce overhead; it is not a promised latency improvement. Report all actual results, cache expiry mistakes and adverse tails. No speculative index, data model, payment behavior or production default changes are justified by these samples.

## Cold key-ring prerequisite and evidence privacy

The first empty-volume run observed alternating401/antiforgery400 across API replicas despite a shared protected key store; recycling both readers made the session portable. The exact framework timing cause is not proven. The lab now materializes the anonymous ring, recycles both API readers before creating any session, then requires authenticated200 from both nodes. A fresh-project rehearsal verifies this prerequisite. This is a lab bootstrap procedure, not a general fix/availability promise for an empty production key ring. Deployment operators must initialize/verify shared keys before admitting browser traffic. Never hide the failure with sticky ordinary API traffic or bypass authentication.

Private logs/TRX/credentials stay under0700 `.local`. k6 summaries and the report publisher allowlist numeric metrics, fixed names, hardware/resource/image identities and static interpretations; they do not export bodies, headers, cookies, fixture accounts, keys, SQL text or arbitrary assertion facts. Refuse publication with missing/failed/skipped cases, unexpected HTTP errors, invalid measurements or broken invariants. Report tiny samples and unmeasured distributions explicitly. Local single-machine shared CPU/disk/network and sequential runs cannot establish production capacity, statistical significance, HA or exactly-once external effects.
