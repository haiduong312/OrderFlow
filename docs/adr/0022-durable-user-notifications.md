# ADR-022: Durable order notifications with a consumer inbox and commit-before-ACK

Date: 2026-11-12. Status: Accepted. Extends ADR-021's independent-consumer boundary; implements milestone 23's local notification delivery as readable user Notifications.

## Context

A confirmed broker message may arrive twice, concurrently, or after newer order events. The consumer may commit PostgreSQL and lose its ACK. A prior inbox existence query cannot protect simultaneous delivery. User notifications also need owner-scoped reads and monotonic read receipts; broker input must not select another user's recipient.

## Decision

Create one local notification for the authoritative order owner for each of seven SchemaVersion 1 order events: created, confirmed, cancelled, expired, processing, shipped and completed. Type is the source event type (the v1 template identity). No Admin broadcast, email, realtime connection, customer refund feature or reporting consumer is added. Notifications stores ID, recipient ID, source EventId, type, order reference and UTC created/read timestamps, with unique `(SourceEventId,Type,RecipientUserId)` plus restrictive user/order FKs. SQL enforces the owner association, immutable identity/content and one-way read receipt. IDs/evidence are retained; destructive downgrade is refused.

Use the fixed consumer identity `notifications.orders.v1`, independently from reporting or payment consumers. Within one scoped PostgreSQL transaction, INSERT the inbox identity with ON CONFLICT DO NOTHING, then SELECT FOR UPDATE and compare message type/schema/SHA-256 of the exact original body. A duplicate with identical facts commits without creating effects; conflicting bytes under the same EventId go to the poison path. A winner that rolls back leaves no handled marker/effects, so a waiting contender can insert and handle it. No uniqueness exception is swallowed inside an aborted transaction.

Validate the envelope/header EventId and Type, JSON content type, <=64 KiB valid UTF-8/object JSON with depth <=32 and no duplicate object properties. EnvelopeVersion=1 and payload SchemaVersion=1 are the only supported versions. Missing/older (including 0)/newer versions are poison, not silently skipped or coerced. Require matching order/aggregate ID, positive matching version, expected status, Ordering/Order provenance and valid trace context. Match recipient to stored order owner and state/version to immutable OrderStatusHistory; do not compare a historical event against the order's latest status. Extra v1 fields may be ignored, but required fields and identities must be valid. Preserve producer trace and correlation/causation when producing NotificationCreated.

Save Notification, handled ProcessedMessages and `notifications.notification-created` outbox atomically; ACK one broker delivery only after successful commit and scope disposal. No broker/email/realtime I/O occurs while the PostgreSQL transaction is open. Transaction/commit uncertainty can lead to redelivery; the same inbox/effect constraints make that safe. Handled notification inbox rows cannot be changed/deleted through ordinary writes. No global consumer ordering or exactly-once transport guarantee is claimed.

Add independent durable notification work/delay/retry/dead queues and exchanges. Publishers declare their bindings even if consumption is disabled, so later worker downtime preserves new work. The existing integration queue is preserved; notification processing does not steal another consumer's copy. Only the seven known order routing keys bind notification work; NotificationCreated cannot recursively feed this consumer.

Notification main -> notification retry exchange -> TTL delay -> notification ready exchange -> retry work -> notification dead exchange -> parked dead queue. Reuse ADR-021's persistent/quorum/at-least-once DLX/reject-publish/delivery-limit policy. Both poison and classified transient database failures NACK(requeue:false); one delayed retry stage then park, with no infinite immediate requeue. A parser/ownership/schema error commits no handled marker. DLQ retains original body/identity and x-death; safe log events identify the classification. Unknown application failures stop the host visibly and leave delivery unacknowledged.

Opt-in `Notifications:Enabled` is independent of `OutboxPublishing:Enabled`. Default one subscription for each work queue, up to four per queue; default prefetch four (1–32) per subscription. Each subscription has its own connection/channel, dispatch concurrency one and `multiple:false` ACK/NACK. Each delivery gets a fresh DI scope/DbContext. Total maximum active transactions is twice ConsumersPerQueue, unacknowledged deliveries at most twice ConsumersPerQueue * Prefetch. Body is fully parsed/used before the callback returns. At most eight connection/session attempts per slot per worker run, backoff 1/5/15/30/60/120/300 seconds, then visible failure/operator restart; authentication/topology errors fail immediately. Shutdown cancellation stops siblings/subscriptions without acknowledging uncommitted work. This is separate from the finite message retry policy.

All authenticated users may list/get/count/read their own notifications; Admin has no override here. The API accepts no recipient ID. Detail/non-owner/missing read returns 404; read is an idempotent conditional update and never resets a read timestamp. Global browser antiforgery remains enabled. List pagination uses existing bounds, stable CreatedAt/ID sorting and a read-only snapshot.

## Consequences and recovery

This is one durable local effect per intended owner/event/type, with at-least-once delivery. Notifications represent event history, not a current-state projection; late/out-of-order notices remain valid and cannot change an order or erase read state. CreatedAt is local processing time, not provider or event occurrence time. Unknown event types are not subscribed; an unexpected delivery on a work queue is poison.

Already Published events from before the new notification binding are not automatically backfilled. Replaying the old integration backlog or DLQ needs a reviewed same-EventId/raw-body process; audited replay tooling remains milestone 28. Do not change whitespace/rebuild the envelope, clear inboxes, generate replacement IDs or delete queues to recover. Business inbox retention/archiving and production TLS/roles/HA remain future operations work. Read UI/realtime delivery and general email remain outside this milestone.
