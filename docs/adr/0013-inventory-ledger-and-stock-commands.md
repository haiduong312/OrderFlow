# ADR-013: Inventory balances, immutable movements and audited stock commands

Date: 2026-11-04. Status: Accepted. Supplements ADR-003/004/012.

## Scope correction

The current request implements stock receipts/adjustments and their admin HTTP/transaction/race evidence in milestone 08, rather than deferring those APIs to 09. It assigns full order reservation behavior to 09, whereas the old roadmap placed reservation schema in 11. Update 09 to include reservation behavior and its necessary Order identity/FK prerequisites; 11 completes order-line snapshots/lifecycle/events on those foundations. Checkout, expiry-worker and payment integrations keep their later milestones. No Order/reservation entity, endpoint, fake production mutation or speculative reservation enum/interface is added in 08.

## Decision

Inventory owns one inventory.Balances row per Product: ProductId PK/restrictive FK, integer OnHand/Reserved, bigint Revision. PostgreSQL checks 0 <= Reserved <= OnHand and Revision >= 0. Available is derived only (OnHand - Reserved); never a stored/client-writable field. Product responses expose advisory Available; Admin inventory detail additionally exposes OnHand/Reserved/Revision. Inventory changes do not increment Catalog version.

Install a PostgreSQL AFTER INSERT Product trigger that creates the zero balance and a zero Initialization movement in the same product transaction. Backfill both active/archived existing products at zero in the additive migration, under its table lock. Every product insertion path, including old API versions/direct EF inserts, gets the same initialization; no opportunistic read-side initialization or invented nonzero stock. Initialization is an explicit System actor, null human ID, fixed reason and operation InitializeInventory:v1/{productId}. Its logical timestamp comes from Product.CreatedAt (already injected/UTC-normalized); migration creates no fabricated human identity or stock history. Future receipts record real stock separately.

StockMovements are immutable facts: independent movement ID, Product FK via balance, operation namespace/UUID, movement kind, actor kind/User FK, normalized reason, OnHand/Reserved deltas, before/after quantities, per-product Revision and UTC occurrence time. Current kinds are Initialization/Receipt/Adjustment; reservation kinds are designed in 09. Admin deltas leave Reserved unchanged. DB checks validate snapshot arithmetic, nonnegative/reconciled row facts and kind/actor/operation shape. BEFORE UPDATE/DELETE and BEFORE TRUNCATE triggers reject mutation; EF also rejects modifying saved movements. Restrictive FKs preserve audit actor/product references. A privileged migration owner can alter/drop triggers/schema; runtime least privilege remains a deployment milestone. No claim that triggers constrain a malicious DB owner.

Receipt requires positive integer quantity; adjustment requires nonzero signed delta. Both require a trimmed nonempty reason <=500 and operationId UUID. Actor comes only from ICurrentUser backed by authenticated Identity cookies, never body/header fields. Admin policy/CSRF applies before application calls. Integer arithmetic uses long for the check, rejects OnHand below Reserved (409 insufficient_stock), and rejects integer/revision overflow (409 stock_limit_exceeded), then writes valid int values. Archived Product/category inventory can still be physically managed by Admin without restoring public visibility.

Use a short Read Committed transaction and InventoryLocking.LockAsync: normalize/deduplicate 1–100 product IDs, lock sequentially in PostgreSQL UUID byte order, read fresh snapshots with AsNoTracking FOR UPDATE, explicitly refresh both current/original values of any previously tracked Unchanged balance, then use tracked EF changes + SaveChanges. Pending unsaved balance edits are rejected instead of discarded. Do not mix ExecuteUpdate with tracked entities. All balance/movement writes share the transaction; no external I/O or unbounded retry. Single-product APIs use the same locking primitive future multi-row reservation work must use. Global lock order remains category/product before inventory; stock-only commands acquire inventory and never later lock Product/Category.

The concrete StockMovements ledger replaces the earlier planned StockHistory composite (OperationId,ProductId,EffectKind) for these admin commands; future reservation effect identities are designed in 09. Unique (Operation,OperationId) is an independent Inventory durable command identity. Receipt/Adjustment share ChangeStock:v1 so changing kind under one ID is a conflict. Compare normalized actor/product/kind/delta/reason. Same ID/body returns original immutable movement with 201, even after later stock changes; changed body/actor/target returns 409 idempotency_conflict. Failed transactions consume no ID. Check before and after locking; cross-product duplicates arbitrate through the unique index, roll back the loser, detach its new movement, reload its tracked balance and only then read the committed winner. Only that named unique violation is classified; unknown database errors remain failures. No generic HTTP replay framework or external exactly-once guarantee is claimed.

History is paginated (default 20/max100/validated offset), sorted by unique per-product Revision DESC, so equal/skewed timestamps cannot reorder effects. Count/page remain sequential statements, not a snapshot across concurrent writes. Init uses Revision0; each admin change increments once. Stock timestamps use a property-specific UTC Z/microsecond JSON converter, not a global numeric/time conversion. Logs do not dump reasons, secrets or request payloads.

## Verification and consequences

Actual PostgreSQL tests cover new-product atomicity, legacy backfill, constraints, immutability including raw SQL/truncate, audited permission/CSRF/validation, reserved boundary/overflow, stale tracked snapshots, failure rollback, operation replay/collision, concurrent removals/receipts and ordered two-row units. Synchronization gates count distinct DbContexts before contested SQL; no arbitrary sleeps. Test-only SQL may model a Reserved balance, but production has no reservation mutation API yet.

Triggers keep initialization consistent across insertion paths but add reviewed migration SQL. Category/catalog version and inventory revision have different meanings; future clients/checkout must re-read/revalidate stock instead of trusting Available. Actor/history data is retained; corrections are new adjustments. Future reservations must extend movement kinds/constraints and transactional ledger reconciliation rather than mutate old facts.
