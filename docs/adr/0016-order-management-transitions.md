# ADR-016: Owner-scoped order reads and PostgreSQL-serialized lifecycle commands

Date: 2026-11-05. Status: Accepted. Extends ADR-003/011/013/015. Implements milestone 13 and pulls the requested Admin fulfillment portion of 19 forward; verified payment confirmation/consumption remains 18.

## Scope and decisions

Expose paginated Customer own orders/detail/cancel and Admin all-order list/detail plus only Confirmed -> Processing -> Shipped -> Completed. Keep the existing /api prefix, CustomerOnly/AdminOnly policies, Identity cookies and global browser CSRF. An Admin is not implicitly a Customer, and dual-role users must still own an order on Customer paths. No paid-order cancellation, refund UI/endpoint, arbitrary status setter, fake confirmation route or worker is introduced.

The existing OrderHistory is the same status audit store now named OrderStatusHistory. Rename its CLR type/table with a reviewed ALTER TABLE migration, preserving every row, PK/FK/index and append-only trigger; do not accept EF's scaffolded DROP/CREATE. Add explicit FromStatus/ActorKind; supported legacy checkout creation facts backfill Customer through a constant ADD COLUMN default, then remove the default so new inserts must supply actor kind. Preserve user ID, timestamp/reason/version. Do not manufacture legacy transitions. The migration is forward-only because downgrade would discard actor/release audit metadata.

Centralize the allowed fulfillment graph and cancellation decision in OrderTransitions, applied through Order methods that increment version and return an immutable status-history fact. Admin requests require an exact status name, positive expectedVersion and optional bounded reason; compare fresh version before applying the graph. Customer cancellation has an empty body, fixed reason and server actor. Already Cancelled returns current representation without new effects, even after the old deadline. Expired returns order_expired; all paid/fulfillment states reject Customer cancellation.

Use one scoped DbContext and short Read Committed mutation transaction. Set transaction-local lock_timeout=5s/statement_timeout=20s. Acquire PostgreSQL Order FOR UPDATE first, with owner predicate on Customer paths, then sample injected normalized UTC. Fresh locked state replaces any unchanged tracked snapshot. If PendingPayment and now>=ExpiresAt, choose Expired; otherwise Cancelled. That locked decision time remains authoritative while waiting for inventory, as ADR-003 specifies.

For cancellation/expiry, lock all target balances in canonical product-ID order using InventoryLocking, then the corresponding reservations in that order. Validate their Active state and immutable order/item quantities/deadlines; inconsistent data fails visibly and rolls back. Release each Active reservation once, decrement Reserved only, increment balance revision and append a linked Customer Release movement. ReleaseStock:v1 uses reservation ID, separate from ReserveStock:v1. Unique operation identity, row bounds, order locking and reservation state/concurrency guards protect durable effects across hosts. Persist per-product releases in the same transaction, so later audit/outbox failure rolls back actual prior SQL.

Store ReleasedAt and Cancelled/Expired release reason, with shape/finite-time checks. Preserve terminal reservation state/metadata through PostgreSQL trigger guards; Released/Consumed cannot reactivate. Append OrderStatusHistory plus one ordering.order-cancelled/order-expired outbox row at the new version, save and commit. An expired cancellation throws the public 409 order_expired only AFTER commit; it must not roll back expiry/release. A duplicate cancelled/expired request creates no second history/movement/event. Admin fulfillment uses the same order lock/version/history/outbox transaction and never touches inventory.

Reuse the existing timeout/SQLSTATE classification and event/snapshot helpers with checkout. Only known PostgreSQL 55P03/40P01/40001/57014 wrappers map to logged sanitized 503; no automatic business retry, shared DbContext across tasks, external network call inside a transaction or exactly-once external-effect claim. After uncertain mutation outcome, cancellation may be retried safely; Admin must refetch current version/state before choosing a next step.

## Reads and expiry presentation

Owner constraints run in SQL before count/paging/detail loading. Lists default to page=1/pageSize=20, maximum 100, ordered CreatedAt DESC, Id DESC; optional status filters match persisted exact status, and only Admin accepts a customerId filter. Reuse PageRequest's supported offset bounds. Page/count and detail/items/history use small Repeatable Read READ ONLY transactions for a consistent snapshot, with statement budgets. No GET locks an order FOR UPDATE, expires a batch or changes reservations.

Keep immutable checkout response DTO/bytes unchanged; extend read DTOs separately. Return persisted status/version/deadline, server observedAt, effectiveStatus/isExpired and endpoint-specific canCancel. PendingPayment at/after its deadline is effectively Expired but remains stored PendingPayment until a safe mutation/worker finalizes it; Cancelled/paid states never become effectively expired merely because the former payment deadline passed. canCancel is advisory and rechecked under the order lock. History exposes server actor kind/UUID, transition timestamp, reason and version, without credentials/payment details. Reads are no-store.

## Verification and remaining scope

Actual PostgreSQL tests cover owner/non-owner/dual-role/Admin/anonymous/CSRF, page/filter/unique ordering, invalid/skipped/reversed/stale/repeated transitions, cancellation boundary equality, duplicate/competing cancellation and shared-stock unrelated orders. Same-order race rendezvous is BEFORE Order FOR UPDATE, not at inventory behind the winner's order lock. Count distinct contexts; only the winning cancellation reaches inventory. One-way arrival observation with a separately held order lock tests decision time after a real lock wait without sleeps. Outbox faults prove SQL release/order/history rollback. Upgrade test verifies history rows and immutability survive rename.

Payment is not implemented. Fulfillment tests seed a Confirmed status/history only in owned test databases to stand in for the future verified payment writer; they do not claim capture/consume correctness. Automatic expiry worker/dispatch, consumption, payment callbacks/refunds, browser UI, process-crash/uncertain-commit fault suite and deployment hardening remain future work. No production seeding/test endpoint was added.
