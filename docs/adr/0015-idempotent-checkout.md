# ADR-015: Atomic idempotent checkout and immutable order snapshots

Date: 2026-11-05. Status: Accepted. Supersedes ADR-004's duplicate-grouping rule, extends ADR-003/009/013/014 and pulls the necessary 09–11/13 foundations into checkout milestone 12.

## Scope correction

The latest request explicitly rejects duplicate product IDs for v1; the original specification/ADR-004 combined duplicates. Reported this contradiction before implementation. Reject duplicates (including differently cased representations of the same UUID) with 400. Keep line/property order and UUID casing normalization for distinct products. No previous checkout endpoint existed, so the operation remains CreateOrder:v1.

Deliver POST /api/orders plus owner-constrained GET /api/orders/{id}, using the existing /api convention and Customer policy. Implement the required Order/OrderItems/OrderHistory, Active InventoryReservations, reserve audit and CreateOrder normalization/replay now. The roadmap marks those portions of 09/10/11/13 as delivered with 12; consume/release/cancel/expiry/fulfillment/payment/listing/worker dispatch remain their later scope. Do not claim the full reservation lifecycle is complete.

## Decision

Use the existing scoped DbContext and shared IdempotencyRecords. Accept exactly items/productId/quantity, 1–100 distinct nonempty UUIDs, integer quantities 1–1000. Validate a single case-sensitive visible-ASCII Idempotency-Key (1–128, no spaces). Canonical JSON fixes version=1, property order, ascending canonical UUID order and integer representation; SHA-256 hashes its UTF-8 bytes. Compare both stored canonical text and hash. Do not include prices/activity or other server state in request identity.

One Read Committed transaction first inserts the InProgress claim under the existing unique user/operation/key index, before any catalog/stock locks. On the named unique violation, roll back/dispose that transaction and detach the losing claim, then query/replay the committed winner outside it. If a contender rolls back instead, PostgreSQL can let the waiting INSERT succeed. No separately committed claim, in-memory mutex, generic retry policy or implicit EF retry. An Order has a unique restrictive CheckoutRequestId FK so a claim cannot back two orders.

Discover product/category associations, then acquire category SHARE locks in canonical UUID order, product SHARE locks in canonical product-ID order, and existing ordered inventory FOR UPDATE locks. SHARE protects price/name/activity/assignment from writers while allowing other checkouts to contend on inventory. Revalidate the locked product's category belongs to the already locked set; on reassignment outside it return 409 state_conflict/rollback rather than acquire an earlier-level lock late. Missing product returns 404; inactive product/category returns 409. Never rely on a stale tracked entity for the catalog or balance snapshot.

After all locks sample injected microsecond UTC time. Create PendingPayment/version 1 with ExpiresAt=CreatedAt+15 minutes and immutable server SKU/name/unit-price/quantity/line-total snapshots. Decimal/UsdMoney computations reject line or aggregate overflow beyond numeric(18,2); public money is formatted decimal strings. Persist order/items/creation history, then reserve each sorted item without changing OnHand. Persist the Active reservation, balance revision and linked StockMovement in that same transaction, one item at a time. A later-item failure rolls back even earlier SQL writes. Existing CHECK 0<=Reserved<=OnHand remains the final row bound.

ReserveStock:v1 uses reservation ID as its independent operation ID. Add Customer/Reservation ledger values and nullable OrderId/ReservationId for old movements; preserve all old rows/triggers. Unique order/product reservation, order-item FK and composite movement/reservation/order/product FK protect identities. SQL triggers plus EF metadata protect item snapshots/history and immutable order/reservation facts; state/version remain available for future lifecycle writers. Cross-row total/reservation/ledger sums are application transaction invariants verified by reconciliation tests, not cross-table CHECKs.

Persist exactly one Pending ordering.order-created outbox row with independent EventId, aggregate ID/version, claim causation UUID, USD total/deadline/status snapshot and no credential/key. Serialize the actual HTTP DTO once into exact UTF-8 bytes, complete the claim with 201/content type/Location/body, save and commit. Return those bytes on first delivery and replay. GET queries by both ID and authenticated owner, returns current status with immutable snapshots, and never expires/releases stock. Replays recheck browser policy/CSRF and do not revalidate current catalog facts or extend deadlines.

Set transaction-local lock_timeout=5s and statement_timeout=20s; provider command timeout stays 30s. Only PostgreSQL 55P03/40P01/40001/57014 (including known EF/Npgsql wrappers) map to logged sanitized 503 with same-key retry guidance; request cancellation remains cancellation. No automatic retry or network call occurs inside the transaction. Unknown failures remain logged/sanitized 500 and roll back. Connection loss near commit is uncertain and is reconciled by caller replay, never assumed uncommitted.

## Consequences and evidence

Shared catalog locks and sorted stock locks favor understandable correctness over maximum throughput. Per-item persistence makes rollback evidence explicit but adds up to 100 roundtrips. Successful response bytes are retained indefinitely and coupled to v1 DTO shape. No external exactly-once guarantee is made. Enum labels for later lifecycle states are storage vocabulary, not implemented commands. Orders/reservations may remain PendingPayment/Active past the deadline while expiry processing is unimplemented; reads preserve conservative stock.

See [checkout transaction/manual guide](../checkout.md) and [implementation status](../implementation-status.md) for acceptance and actual run results. PostgreSQL tests cover duplicate/conflicting keys, two-host last-unit contention gated immediately before inventory FOR UPDATE, after compatible catalog SHARE locks, partial SQL rollback, mandatory outbox failure/503, price/snapshot immutability, tampered fields/CSRF/ownership, category reassignment and logical time after a pause. The progressed-state replay test uses test-only SQL to model a future writer; it is not evidence of payment/fulfillment transitions.
