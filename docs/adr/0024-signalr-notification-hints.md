# ADR-024: Authenticated notification hints through API-hosted RabbitMQ and Redis SignalR

Date: 2026-11-13. Status: Accepted. Extends ADR-022's durable Notifications with the explicitly requested optional realtime backend. Frontend integration stays a later milestone-23 slice; proxy configuration is assigned to milestone 26 by the latest request.

## Context

A Worker process cannot address connections held by another process through its own in-memory hub. NotificationCreated already commits through the outbox. Realtime is optional: durable Notifications/owner HTTP APIs and orders remain authoritative even when broker/Redis/connections fail. A successful backplane publish is not a client/business acknowledgement.

## Decision

Only the API registers NotificationHub and IHubContext. A separate API-hosted RabbitMQ consumer reads NotificationCreated from its own durable work/delay/retry/dead topology. Competing API consumers share the same queues, so one consumes each delivery; the official Microsoft.AspNetCore.SignalR.StackExchangeRedis backplane reaches user connections on all configured API instances. No Worker hub or direct worker-to-socket connection exists.

Move existing RabbitMqSettings/Topology and the small shared async subscription transport into Application/Messaging (the existing infrastructure folder boundary). Worker keeps its thin notification facade/processor; API and Worker still do not reference each other. RabbitMQ.Client remains 7.2.2; all generated project locks reflect the shared dependency. Publishers declare the realtime queue/binding before sending future events. Existing topology is preserved; only notifications.notification-created binds the new work queue.

Hub path /api/hubs/notifications requires the existing Identity cookie. IUserIdProvider uses the existing strict UserIdentity reader: one authenticated identity, one nonempty GUID NameIdentifier, canonical UUID D formatting. No client-provided destination/user/order ID, subscription/group API or business mutation method is exposed. Unknown Subscribe/JoinOrderGroup invocations fail. Clients cannot join another customer's order group because no order groups are exposed.

Support WebSockets with normal negotiation, no SSE/LongPolling fallback. Apply server authorization to negotiate/connect, HTTPS unless the existing Development-only opt-in is used, same-origin Origin validation for browser WebSocket/HTTP requests, explicit antiforgery on unsafe negotiation requests and existing bounded auth-read rate policy. No query access_token/JWT authentication. Browsers must use the current cookie and a fresh X-CSRF-TOKEN for negotiation. Nonbrowser authenticated clients may omit Origin; browsers send it. CloseOnAuthenticationExpiration closes expired sessions, and application stopping aborts connections. Hub has bounded buffers/receive size/parallel invocation/handshake/timeout settings and detailed errors disabled. Frontend must stop its connection on logout; cookie/security-stamp/role changes are not continuously revalidated on an already established socket, per SignalR's documented model.

Parse <=64 KiB strict UTF-8 JSON/depth 16/no duplicate keys and supported EnvelopeVersion/SchemaVersion 1. Verify header/body identity/type/provenance and NotificationCreated identities/timestamp; query the durable Notification in a fresh scoped DbContext and compare recipient/source/order/type/time. Derive destination from stored recipient, not untrusted payload alone. Dispose the scope before IHubContext network dispatch. Send only NotificationAvailable `{eventId,notificationId,orderId}` via Clients.User. No email/body/type/amount/recipient/trace data is copied to the browser hint. ConnectionReady has no payload and signals that the backplane subscription is established; clients refetch durable state at this boundary/reconnect.

Do not create another ProcessedMessages handled marker for hints. Redis/client delivery cannot be atomic with PostgreSQL and dedup-before-send could hide a lost attempt. Duplicates retain stable IDs and are acceptable. ACK after a dispatch attempt succeeds, not after client processing; no connected user can still be a successful attempt. Redis/dispatch timeout or classified transient DB failure NACK(requeue:false) through one delayed retry then parked DLQ. Malformed/unsupported/mismatched events follow the same finite poison path. Unknown failures fault the host visibly. Two subscriptions/API (main and retry), sequential per channel, prefetch default 4 (1–16), fresh DB scope per delivery, eight broker session attempts with bounded backoff and shutdown cancellation.

Use official Redis backplane/client 10.0.15, compatible with pinned .NET 10 SDK/runtime. 10.0.14 backplane was flagged by NuGet/Microsoft advisory GHSA-wr8v-9x5q-ggcm; do not introduce it or suppress auditing. Existing EF/ASP.NET package pins and SDK remain otherwise unchanged. Redis 8.10.3-alpine is pulled/digest pinned in a loopback development Compose service. Redis is ephemeral (no persistence) and never the notification store. Configure matching environment-specific channel prefixes, AbortOnConnectFail=false, short connection/command budgets and BacklogPolicy.FailFast; no offline hint buffering claim. Dependency logs use safe code/type/instance/IDs, omit raw connection strings/SDK exception text in our logs, and suppress noisy framework HTTP/SignalR logs that can expose connection tokens.

## Affinity/deployment boundary

Redis does not remove affinity requirements for normal negotiation. Milestone 26 must configure the proxy so negotiate and WebSocket connect for one connection reach the same API, preserve Upgrade/Connection and Origin, set suitable idle/buffering behavior, trust forwarded headers only from configured proxies, and share protected Data Protection keys/application name across API instances for cookie/antiforgery continuity. No proxy/shared-key deployment is implemented here. The exception for all clients using WebSockets with SkipNegotiation=true is documented upstream but is not the supported client contract for this milestone.

The reproducible test uses two actual Kestrel API hosts with independent DI/hub managers and real RabbitMQ/Redis, sharing only test cookie-key material and PostgreSQL. API A consumes while B owns user connections. It is not an independent OS-process/cluster failure claim. The runbook supplies two separate API-process commands; production reverse proxy is still milestone 26.

## Consequences

Outbox Published means broker handoff. Hint dispatch completion means at most an attempted backplane handoff, never exactly-once/durable client delivery. Redis outage can lose hints while durable notification/order HTTP remains available. Existing sockets may remain connected across a Redis outage; frontend should also refetch on focus/manual refresh or a suitable polling policy, not derive durable unread counts from hint increments. Reconnect always refetches, deduplicates by stable IDs and uses owner HTTP authorization. Offline users receive no buffered realtime history; only durable data provides catch-up.

No frontend/client package/application, business state mutation, general event replay, notification re-creation, email behavior change, database migration, production proxy/TLS/backplane roles/HA or continuous connection revocation infrastructure is added. Old Published NotificationCreated events predating the new queue are not automatically replayed.
