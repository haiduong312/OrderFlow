# ADR-010: Identity browser sessions and explicit development bootstrap

Date: 2026-11-02. Status: Accepted. Supplements [ADR-002](0002-browser-authentication.md) and [ADR-009](0009-postgresql-reliability-foundations.md).

## Context and decision

Milestone 04 delivers register/login/logout/me and antiforgery endpoints using the existing Identity PostgreSQL tables. No migration or dependency change is needed. Identity owns password hashing, normalization, password validators, lockout and security stamps. No custom password store, JWT, refresh token, external login or public role management is introduced.

Register accepts only email/password, trims email, uses it as UserName, and assigns Customer in the same transaction as account creation. Unknown fields are rejected. Roles must already be provisioned. Case normalization plus the unique normalized username index resolves concurrent duplicates; only that known unique violation is mapped to safe registration validation. Other infrastructure exceptions remain failures. Registration does not sign in. A duplicate returns generic 400; v1 does not promise registration enumeration resistance.

Login serializes the existing user's password check/lockout update with PostgreSQL FOR UPDATE in a scoped context/short transaction. This avoids losing failed-attempt increments across API processes. Two-host tests synchronize before both lock statements execute. Cookie issuance is after commit; there is no external network call in the transaction. Standard Identity methods have no CancellationToken argument: propagate cancellation to explicit EF queries/transactions and check around Identity calls. Identity's own lockout implementation uses framework UTC wall time; application CreatedAt and cookie expiry use injected TimeProvider. Tests expire stored lockouts directly without sleeps. MFA-enabled accounts cannot bypass MFA through this password-only endpoint; MFA enrollment is deferred.

Cookie tickets are nonpersistent browser sessions, capped at 8 hours without sliding renewal; security stamps are checked every 5 minutes. Auth cookie is host-only, Path=/, HttpOnly, SameSite=Lax, Secure, with a __Host- name. Default Development also uses HTTPS. Explicit AllowInsecureHttp is rejected outside Development and switches to separate Dev cookie names with SameAsRequest for loopback-only verification. No permissive CORS or trusted forwarded-header configuration is added.

ASP.NET Core IAntiforgery creates/validates the cookie/request-token pair. A global JSON MVC authorization filter validates unsafe methods, including anonymous registration/login; it converts only AntiforgeryValidationException to a safe 400. AddControllers alone does not register MVC's view antiforgery filters, so we call the supported IAntiforgery API rather than add Razor/views. IgnoreAntiforgeryToken remains the explicit policy override for future signed webhooks; foundation test probes alone use it today. Refresh tokens after login/logout; HttpOnly cookies are never read by React. Framework role policies return API 401/403, never redirects. Ownership queries remain the responsibility of later order features.

Fixed-window authentication limits are per remote IP, per process: writes 20/minute shared across register/login/logout, reads 60/minute shared across token/me; no queue. Rejections use 429 ProblemDetails and Retry-After. These are neither cluster quotas nor full brute-force protection. Standard account lockout adds 5 failures/15 minutes; unknown and locked accounts use the same generic 401. No raw forwarded IP is trusted.

Account seeding is an explicit Worker command, Development-only and disabled by default. Email/password/role must come from private configuration; Identity validates password strength. Existing accounts are not reset/promoted, and mismatched roles fail. Normal startup never seeds. Production role/Admin provisioning is an operator responsibility, not a production default password.

Data Protection sets the application discriminator OrderFlow. The framework's local key ring is sufficient only for the current single-host development setup. Per the current request, **milestone 26** must implement shared durable keys, access controls/encryption at rest and compatible replica configuration, alongside TLS/trusted-proxy deployment hardening. This extends the previous milestone-26 fault-suite scope; milestone 25 remains local composition. We do not claim multi-replica cookie readiness now.

## Consequences and verification

Keep the small HTTP/session coordinator in API/Auth because it issues Identity cookies; shared Identity policy/bootstrap remains in Application/Modules/Identity. No generic auth repository or extra abstraction layer is needed. Row locking trades concurrent logins for correct per-account lockout. Default Identity PBKDF hashing stays upgradeable by the framework. Logout clears this browser's cookie; it is not immediate revocation of copied tickets on every device. Email verification/reset, MFA enrollment, all-device revocation and distributed rate limits remain deferred.

Tests use actual PostgreSQL and ephemeral Data Protection only inside isolated test hosts. Test-only role probes verify Customer/Admin separation without shipping dummy protected business endpoints. See [authentication runbook](../authentication.md) and [implementation status](../implementation-status.md) for evidence/limits.
