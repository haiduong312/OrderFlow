# ADR-035: Acceptance audit, explicit key bootstrap and portfolio handoff

Status: accepted, 2026-11-17. Scope: audit completed work, fix material reproduction gaps and document actual behavior; no public deployment or new business platform.

## Decisions

1. Treat the baseline spec as obligations, not an implementation checklist automatically satisfied by milestone labels. Mark A16 standalone stock integration events, A18 enriched order envelope and A19 generic operational failure/replay scope partial. Existing stock ledger, minimal order events, direct reports and email-only retry remain supported. A24 documentation/handoff can be delivered while those gaps remain visible. Correct stale endpoint/current-state prose rather than inventing missing routes/projections.
2. Address the previously observed empty-key-ring bootstrap gap with a serial explicit API CLI `initialize-deployment-keys` / Compose `initialize-keys`, before cold API replicas. Reuse deployment validation, same protected key directory/application discriminator/certificate and supported IDataProtectionProvider Protect/Unprotect. Do not start HTTP/background jobs, migrate a DB, expose a public test hook or log key material. Repeat invocation verifies existing usable keys. Normal Data Protection lifecycle still manages rotation; this is not a distributed generation lock or production key lifecycle solution. Update deployment verification/load startup to use the one-off step. Independent-provider regression and fresh real replica session/CSRF checks verify the narrow guarantee.
3. Provide a small explicitly disposable demo helper using existing private setup/client facilities, fixed loopback ports/subnet, UUID project/run marker, generated .invalid identities, real API/CSRF fixture seed, no-redirect provider operator calls and volume-preserving cleanup. Persist original normalized checkout/payment key/body before I/O; an uncertain result never causes silent replacement. No live provider/email, real data, arbitrary URL/SQL/job executor or browser control secret. A real built-UI Playwright rehearsal uses separate accounts and only the generated TLS public-key pin; no fake successful responses or production failpoints.
4. Keep README concise with exact quick-start/schema/seed commands, safe accounts, actual architecture, API docs and design links. Put three accurate transaction diagrams, a5–8-minute human demo, code-grounded interview answers, CV-to-code/test map and remaining/v2 scope in focused documents. Omit benchmark numbers from CV bullets; existing reproducible local report shows adverse cache/latency results and has single-machine limits.
5. Run appropriate final checks after fixes, record actual local execution separately from historical/remote/unmeasured claims. No package/migration/SDK upgrade or unrelated rewrite. Retain existing user data/volumes; no commit/push or publication.

## Limits

The ring-init command requires the operator to run it serially before admission and to preserve protected storage/certificate/application identity. It does not prove arbitrary concurrent cold start, live rotation/revocation, multi-host key storage, backup/restore or production availability. A connected demo socket plus UI update may also use polling fallback; existing transport/replica tests separately prove actual hints. Test ACK/channel/SQL boundary failures are not exact OS-kill evidence. General operational replay and event contract gaps remain pending, not implicitly moved into completed v1.
