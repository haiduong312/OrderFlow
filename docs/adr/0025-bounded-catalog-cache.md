# ADR-025 — distributed-only, bounded catalog cache-aside

Date: 2026-11-13. Status: accepted for the requested catalog caching milestone.

## Context and scope correction

The original v1 exclusion in the specification excludes Redis/distributed caching. ADR-024 already permits Redis as a SignalR backplane; this request additionally permits optional catalog caching. This record supersedes only that exclusion for public Product/Category **detail** reads. It does not authorize general filtered-list, checkout, account, order, authorization or inventory caching. No database model/migration, frontend or worker change is needed.

## Decision

Use .NET 10 `IDistributedCache` with the stable Microsoft.Extensions.Caching.StackExchangeRedis **10.0.15** provider, pinned centrally and in lockfiles. The installed SDK is 10.0.115/runtime 10.0.15; existing EF/Identity pins remain unchanged. Choose explicit cache-aside over HybridCache because this small scope needs neither local memory nor stampede machinery. HybridCache's distributed invalidation does not evict another server's L1. We have **no L1** and read Redis on each eligible detail request.

Public product cache entries contain only ID, SKU, name, description, decimal price, CategoryId, activity and version. They contain no category display snapshot or inventory. Read category details through a separate category key; compose ProductResponse and read Available separately from PostgreSQL every time. Admin reads and all lists bypass cache. Disabled cache retains the original single joined product query. Checkout still reads/locks PostgreSQL catalog and balances and computes authoritative totals itself.

Keys are `{environment-prefix}catalog:v1:product:{uuid-N}` and `{environment-prefix}catalog:v1:category:{uuid-N}`. UUIDs are canonical lowercase N form, fixed key lengths; the configured prefix must match across API nodes of one deployment and differ across environments/databases. Values are UTF-8 camelCase System.Text.Json envelopes `{validUntil,value}`, depth <=8, required constructor fields, <=16 KiB. Internal product price is a JSON decimal number deserialized directly to .NET decimal; HTTP money remains the existing invariant two-place USD string. Product/Category DB field bounds also constrain normal serialization. Missing/inactive source entities are not cached; active product fields may be cached even while their category hides the public response; there are no user-derived filter keys or private values.

Both entries have a **30-second absolute lifetime**, no sliding renewal. Compute `validUntil` immediately before the source SELECT, not after it. Do not store a load that has already passed its deadline. Set the same absolute expiration in Redis and reject expired envelopes at lookup (`now >= validUntil`), even if Redis retains bytes. This also bounds a delayed write after invalidation without extending its old snapshot's freshness window. Reject oversized/malformed entries and read PostgreSQL. IDistributedCache reads the complete byte array before our size check; the limit bounds our writes/deserialization, not memory allocation from a malicious Redis server. Redis is a trusted dependency; production operators still need ACL/TLS and memory/eviction limits.

After successful create/update/archive (including restore/reassignment), remove the affected Product or Category key **after DB commit and transaction disposal**. No fan-out: category changes invalidate only the category key, as product entries contain just CategoryId. Failed SQL writes do not invalidate. No Redis calls are added inside business transactions. No invalidation outbox or background job is introduced.

## Exact consistency contract and failure behavior

With a successful removal and no concurrent stale refill, a subsequent read on any API node sees the committed edit/archive. This is **bounded stale presentation**, not linearizable catalog reads: a source SELECT that preceded the commit can SET its old value after DELETE. A crash/cancellation between DB commit and invalidation, a failed DELETE, or a writer bypassing CatalogService also leaves old entries. At lookup, old cache data is accepted for at most **30 seconds from the start of its source read**, assuming synchronized/nondecreasing host UTC clocks. Consequently an edit can remain unseen for up to the remaining original 30 seconds. A delayed stale SET can displace a newer entry temporarily but cannot renew its deadline. Already in-flight HTTP/DB work can complete later; this is a lookup freshness bound, not a wall-clock response-delivery guarantee. Independent product/category reads are not an atomic snapshot, and public lists (uncached) can become fresh before a detail. Archived display/prices can briefly remain visible; stock reservation, eligibility and payment decisions still use PostgreSQL immediately.

Get/Set/Remove catch only Redis connection/server/timeout and Socket cache failures at the cache operation boundary. SQL delegates execute outside those catch blocks. Cancellation and unexpected programming/configuration failures propagate. Failed GET goes to PostgreSQL and suppresses the futile SET for that load; failed SET returns the successful DB read; failed DELETE keeps the committed mutation successful with a warning. There is no application-level operation retry or disconnected command backlog; normal multiplexer reconnection remains available for later requests. Redis connect/command budgets are 250ms, ConnectRetry=0, BacklogPolicy.FailFast; transport/scheduling can add overhead, so these are SDK budgets, not an HTTP latency SLA. Miss stampedes across processes can issue duplicate reads; short TTL and small scope are preferred over coordination complexity here.

Structured warning 2501 records operation/kind/exception **type only**, not SDK exception messages, connection strings or payloads. Warning 2502 records invalid payload kind. Meter `OrderFlow.CatalogCache`, counter `catalog_cache_operations`, uses bounded `kind` (product/category) and `outcome` labels: hit, miss, set, remove, get_failure/set_failure/remove_failure, invalid_payload, oversized. Cache availability is optional and does not change checkout readiness or durable state.

## Evidence and costs

Real PostgreSQL/Redis tests run two independent Kestrel API hosts sharing only DB/Redis and a logical test clock. They cover cross-node hits/edits/archives/restores/reassignment, failed invalidation, live inventory and stock rejection, Redis stop with DB fallback, and SQL failure propagation. A TCS gate pauses old SET after its source SELECT; mutation/DELETE completes before release. The test observes permitted stale data and refuses it at the exact logical deadline without sleeps. This is not an independent OS-process kill/cluster-failover test.

The repeatable scenario is ten category detail HTTP reads: compare actual EF SELECT counts with cache disabled/enabled; see [runbook](../catalog-caching.md) and [executed status](../implementation-status.md). Product detail still performs one live inventory query on each hit. A cold product miss performs **three** SELECTs (fields/category/inventory), versus one joined SELECT with caching off; ten reads from cold cost 12 statements versus 10 uncached, though product/category catalog projections each run once instead of ten joined reads. No overall product latency/throughput improvement is claimed. Filtered lists remain uncached until their invalidation can be managed.

The installed StackExchange.Redis 2.7.27 RedisTimeoutException derives from TimeoutException, independently of RedisException; classify it explicitly, without swallowing general DB timeouts. Tests cover GET/SET timeout fallback and DELETE timeout staleness.
