# Interview guide: explain the code that exists

Use the [flow diagrams](flows.md), [acceptance audit](acceptance-audit.md) and [demo](demo.md) together. These are short answers, not claims that every production concern is solved.

| Question | Answer grounded in this repository |
| --- | --- |
| Why a modular monolith? | API/Worker share feature folders and one scoped EF Core context, making one PostgreSQL unit of work practical for stock/order/history/outbox. Separate processes serve HTTP/background I/O; the simulator has a genuinely independent provider DB. This is not a microservices/event-sourced platform. |
| How is overselling prevented? | `CheckoutService` arbitrates the unique user/operation/key, locks category/product eligibility and sorted stock balances, then reserves all lines inside one transaction. `InventoryBalance` plus SQL constraints/append-only movements enforce0<=Reserved<=OnHand. Available from a cart/cache is never authority. |
| What happens if the second line has no stock? | Earlier actual SQL writes are rolled back with the whole transaction, including order/key/history/outbox. `CheckoutPersistenceTests` inject failures after real first-line work. |
| Why canonical item order and multiple lock levels? | Normalize distinct product UUIDs and quantities for request identity and consistent row ordering. Checkout uses category→product→balance; existing-order commands start with Order. StartPayment is Order-first, not checkout's insert-first protocol. See `InventoryLocking`, `OrderLocking`, `PaymentSettlement`. |
| How does a duplicate checkout replay? | `IdempotencyRecords` has a unique user/operation/key. Compare canonical body plus SHA-256, store exact successful201 bytes/content type/Location. A concurrent loser rolls back its failed transaction before reading the winner. Same key/different valid body is409. No expired-key reuse policy exists in v1. |
| Does an expired order change the replay response? | No: replay returns the original PendingPayment snapshot. Owner GET returns current authoritative state. Rebuilding a response from today's product/order would break the contract. |
| Why persist the frontend intention? | A timeout does not tell the browser whether commit happened. `checkout/pending.ts` keeps exact normalized body/key per user before POST and fences account/tab changes; modified cart needs explicit resolution/abandonment. Disabled buttons and Web Locks are UX, not SQL correctness. |
| How are auth and cross-account caches handled? | Identity HttpOnly secure cookies, anonymous/authenticated antiforgery, server roles/owner-constrained queries and404 for non-owned resources. Session changes cancel/purge/fence private Query data before another user renders it. Zustand stores no auth token/authoritative role; the bounded device cart is deliberately shared. |
| Why does reservation equality expire? | `now >= ExpiresAt` is due, after acquiring the existing Order lock. Settlement freezes that decision through inventory waits; the UI timer and provider occurrence time cannot authorize confirmation. Test clocks/gates verify before/equal/after and actual wait participants. |
| What if payment captures after cancellation/expiry? | Persist a valid USD capture as unallocated, create one full-compensation refund intention by capture identity, never consume released stock or resurrect the order. Unknown references/currencies are quarantined. Capture evidence is monotonic even after an earlier failed observation. |
| Where are the network boundaries? | Payment/refund/email/outbox: short claim transaction commits, external I/O happens outside it, then a fresh context/guarded completion records the outcome. Callback receipt and later settlement are separate transactions. One DbContext is never shared across concurrent tasks. |
| What does a lease guarantee? | A new token fences an old owner after reclaim; it cannot stop a provider that already accepted a send. Payment/refund may finish after deadline if the original token is still current; outbox/email also require unexpired ownership. Unique local effects and provider keys are still needed. |
| Why not retry every exception? | Npgsql has no implicit business retry. Checkout returns classified contention503; outbox/payment/refund/email have finite typed retry policies. Uncertain financial requests retain original keys and use lookup; permanent/exhausted work becomes Failed/NeedsReview. Unexpected exceptions surface. |
| What happens after publish/DB commit but before ACK? | A lost confirm can republish the same EventId; committed consumer effects then lost ACK can redeliver. Notification inbox `(ConsumerName,EventId)` and local unique constraints make the second local handling a no-op. Broker handoff is not business completion. |
| Is delivery exactly once? | No. PostgreSQL can atomically deduplicate local effects; a capable provider honors stable payment/refund keys. SMTP has no idempotent-send/lookup, so a lost response can duplicate accepted mail. SignalR hints can duplicate/drop; clients refetch durable state. |
| Why not store reports from events? | `ReportingService` uses bounded direct EF/parameterized SQL projections in read-only Repeatable Read. No projection/replay checkpoint exists. Captured revenue includes all stored verified captures; paid sales only allocated winning ones; refunds only Succeeded cash movements; net is captured minus refunded in UTC interval. Completed orders are not a revenue source. |
| What can cache and invalidation guarantee? | Only catalog product/category detail DTOs, JSON<=16KiB/absolute30s source deadline, distributed-only/no L1. Mutations invalidate after commit; stale refill/deletion failure can persist to the original deadline. Availability stays PG-backed; cached fields never authorize checkout. Only cache exceptions fall back; SQL errors propagate. |
| Why did local Redis not make requests faster? | Small indexed projections were cheap; cached product reads still need inventory and two Redis lookups. The recorded workload reduced catalog SQL, but showed worse HTTP latency/rate. One machine/quota/JIT/GC/short sample is not a production capacity experiment. See the reproducible report rather than inventing percentages. |
| Why share keys and initialize before replicas? | A shared DB does not share cookie encryption. APIs need the same protected Data Protection directory/application identity/certificate. `initialize-deployment-keys` materializes/verifies the ring once before cold readers serve traffic. It does not solve certificate rotation, secret-at-rest or multi-host storage by itself. |
| Does Redis remove SignalR affinity requirements? | No. Negotiation/upgrade token state remains node-local. nginx pins the supported negotiated WebSocket hub path; Redis fans user-specific hints across nodes. Replacing a node requires reconnect/durable catch-up. SSE/long polling are not enabled/tested. |
| Which operational replay APIs exist? | Only narrowly scoped audited email retry. Per-order payment/refund audits are read-only. There is no generic SQL/job/outbox/refund retry executor; remaining operational obligations are explicitly partial. |
| What was verified versus deferred? | Real PostgreSQL/HTTP/constraints/concurrency, real broker/Redis/Mailpit, browser flows, replicated local TLS and bounded failure tests. Remote GitHub execution, production traffic/HA/backups, real provider/email, enriched order/standalone stock event obligations and general operational replay remain outside verified completion. |

Before claiming concurrency in an interview, locate the actual SQL/interceptor rendezvous and show both participants arrived; a sleep or two asynchronous tasks alone is insufficient. Before claiming a benchmark improvement, show the exact scenario, dataset, hardware/quota/cache state and repeat result. Before presenting a CV bullet, follow its [code/test map](cv.md).
