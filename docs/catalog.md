# Catalog — milestone 07

Products and Categories are implemented with PostgreSQL storage, explicit DTOs, public reads and Admin cookie/CSRF-protected writes. See [ADR-012](adr/0012-catalog-products-categories.md), [authentication setup](authentication.md) and [migration/setup guide](persistence.md). Milestone 08 adds actual advisory Available plus [Inventory commands/history](inventory.md); full reservations/checkout, Order snapshots, cache and uploads remain later features.

## API

All paths start with /api. List query names are case-insensitive; examples use camelCase.

| Method/path | Permission | Body / result |
| --- | --- | --- |
| GET /products | Public | q, categoryId, page, pageSize, sort; paginated ProductResponse |
| GET /products/{id} | Public | Visible ProductResponse or generic 404 |
| GET /categories | Public | q, page, pageSize, sort; paginated CategoryResponse |
| GET /categories/{id} | Public | Active CategoryResponse or generic 404 |
| GET /admin/products | Admin | Same product filters; includes archived/hidden products |
| GET /admin/products/{id} | Admin | ProductResponse, including own/category activity and version |
| POST /admin/products | Admin + CSRF | sku/name/description/price/categoryId; 201 + Location |
| PUT /admin/products/{id} | Admin + CSRF | name/description/price/categoryId/isActive/expectedVersion; 200 |
| POST /admin/products/{id}/archive | Admin + CSRF | expectedVersion; 200 archived representation |
| GET /admin/categories | Admin | Same category filters; includes archived categories |
| GET /admin/categories/{id} | Admin | CategoryResponse and version |
| POST /admin/categories | Admin + CSRF | name; 201 + Location |
| PUT /admin/categories/{id} | Admin + CSRF | name/isActive/expectedVersion; 200 |
| POST /admin/categories/{id}/archive | Admin + CSRF | expectedVersion; 200 archived representation |

No DELETE endpoint exists. Opaque UUID identifiers are generated by the server. Product SKU is normalized before persistence: trim then ASCII uppercase, 1–64 ASCII letters/digits/hyphens; immutable after creation. A unique database index reserves SKU globally, including archived products. Required trimmed names are 1–200 characters; description is optional, trimmed and stored/returned as empty text when omitted, maximum 2000. HTTP input bounds also apply before trimming. Category labels are not unique; use IDs for references/filtering.

Price must be an invariant JSON string, >0 through 9999999999999999.99, no more than two fractional digits. Output always has two digits and currency USD. Shared typed money handling is preserved; unrelated numeric fields stay JSON integers/numbers. JSON number, null, zero, negative, exponent, grouping or excess scale is 400. Unknown request fields are rejected, including sku on update, id, currency, onHand, reserved and available. Catalog writes never mutate stock. Product responses expose actual derived Available from milestone 08; Admin reads OnHand/Reserved through the Inventory endpoint. No fictitious stock count is returned.

Admin policy checks run before controller work. Anonymous writes/admin reads return 401; Customer admin access returns 403; missing/invalid CSRF for an authorized Admin write returns 400 antiforgery_failed. Validation returns 400 validation_failed; missing URL resource returns 404 not_found; nonexistent body categoryId is 400 validation_failed; inactive target category is 409 state_conflict. Duplicate SKU returns 409 sku_conflict. Unknown DB/infrastructure failures retain sanitized 500, not a manufactured conflict. Errors retain traceId, errors and application/problem+json regardless of success response metadata.

## Archive and concurrency

- Public visibility is Product.IsActive AND Category.IsActive. Archive/missing public detail both return generic 404. Public lists omit hidden rows; empty active categories remain visible.
- Admin list/detail includes active/archived rows. Product response includes Category.IsActive so Admin can distinguish individual product archival from category hiding.
- Archiving a category does not rewrite products or increment their versions. Restoring it via PUT isActive=true makes only individually active products visible again. Product restoration also uses PUT. Product content edits/creation require an active target category; product archive is allowed under an inactive category.
- Every update/archive requires a positive expectedVersion. New entities start at 1; update increments once; stale expectedVersion returns 409 version_conflict. Archive changes active to false and increments once; repeating it with the current version is a no-op. Repeating with a stale version still returns 409. At int.MaxValue, further state changes return state_conflict.
- EF uses Version as a concurrency token. No-op archive still executes a version-conditional UPDATE to detect a concurrent restore. Product create/update takes a PostgreSQL Category FOR UPDATE lock and reads fresh state with AsNoTracking before saving. This serializes assignment against category archive and prevents stale tracked Category state from approving a write.
- No external network calls occur inside these transactions. SKU uniqueness is enforced by PostgreSQL, not an in-process lock or an existence-check race. Category row locks add contention for edits in the same category; future throughput changes must preserve the guard.

## Search, ordering and query plans

q is optional, at most 100 characters before trimming; whitespace-only means no search. Products match name OR SKU; categories match name. PostgreSQL ILIKE performs case-insensitive **literal substring** search according to the database collation. Backslash, percent and underscore are escaped. There is no accent removal, stemming, token ranking or SQL wildcard language in user input.

Products accept categoryId as an exact UUID filter. Unknown category produces an empty page, empty UUID/malformed UUID returns 400. Public filters never enable archived visibility. Products support newest (default), name, price-asc and price-desc; categories support newest/name. Invalid sorts return 400.

| Sort | SQL ordering |
| --- | --- |
| newest | CreatedAt DESC, Id DESC |
| name | Name ASC, Id ASC |
| price-asc | Price ASC, Id ASC |
| price-desc | Price DESC, Id DESC |

Page defaults to 1; pageSize defaults to 20 and must be 1–100. Offset must fit signed int. Past-end page is empty with filtered totalCount. Filtering precedes count/order/paging, and all read queries project DTOs with AsNoTracking. Count/page statements run sequentially on one scoped context; they are not a snapshot across concurrent writes. Stable ordering prevents ties on unchanged data, not page drift during edits.

B-tree indexes: unique C-collated normalized SKU; (CreatedAt DESC, Id DESC) on both tables; (CategoryId, CreatedAt DESC, Id DESC) on Products. These support uniqueness/exact SKU lookup and applicable category/order patterns. Ordinary B-tree does **not** accelerate ILIKE '%keyword%' arbitrary substring search. Name/price sorts and keyword queries may scan/sort; small-catalog baseline is intentional. No search benchmark or plan guarantee is claimed. A measured need may justify pg_trgm/GIN later; no extension is installed now.

For local plan inspection use parameterized/adapted SQL against disposable/sample data, for example:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT p."Id", p."Name", p."Price"
FROM catalog."Products" p
JOIN catalog."Categories" c ON c."Id" = p."CategoryId"
WHERE p."IsActive" AND c."IsActive" AND p."Name" ILIKE '%sample%'
ORDER BY p."CreatedAt" DESC, p."Id" DESC
LIMIT 20;
```

ANALYZE actually runs the SELECT. Tiny tables often prefer sequential scans; an index existing does not prove a query uses it.

## Response and manual walkthrough

Example ProductResponse (UUIDs illustrative; Available is advisory):

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "sku": "DEMO-001",
  "name": "Demo keyboard",
  "description": "Local portfolio sample",
  "price": "49.90",
  "category": {"id": "22222222-2222-4222-8222-222222222222", "name": "Keyboards", "isActive": true},
  "isActive": true,
  "version": 1,
  "available": 0,
  "currency": "USD"
}
```

Lists return {items,page,pageSize,totalCount}; counts/versions are integers. No image field is needed, so no asset/upload/provider dependency is added. OpenAPI is Development-only at /openapi/v1.json and describes actual registered request/response types, positive string prices, required fields, pagination bounds and error responses; Production remains 404.

1. Follow README locked restore/build and [persistence](persistence.md) to start PostgreSQL and apply the dedicated EF migration step, including **20261103093358_AddCatalog**. API/worker never migrate on startup. Existing data/volumes are preserved; do not run Down/reset against data you want to keep.
2. Follow [authentication](authentication.md) to explicitly seed a Development Admin from private configuration, log in with a private cookie jar and fetch a fresh authenticated CSRF token. Reuse that guide's ORDERFLOW_AUTH_URL, ORDERFLOW_AUTH_JAR and orderflow_csrf function; run these commands before its cleanup step.
3. Create a category, then use its returned ID to create a product:

```bash
ORDERFLOW_CSRF=$(orderflow_csrf)
curl --fail-with-body -i -b "$ORDERFLOW_AUTH_JAR" -c "$ORDERFLOW_AUTH_JAR" \
  -H 'Content-Type: application/json' -H "X-CSRF-TOKEN: $ORDERFLOW_CSRF" \
  --data '{"name":"Keyboards"}' "$ORDERFLOW_AUTH_URL/api/admin/categories"
# Assign the returned ID (not the illustrative UUID above).
ORDERFLOW_CATEGORY_ID='<returned-category-uuid>'
curl --fail-with-body -i -b "$ORDERFLOW_AUTH_JAR" \
  -H 'Content-Type: application/json' -H "X-CSRF-TOKEN: $ORDERFLOW_CSRF" \
  --data "{\"sku\":\"DEMO-001\",\"name\":\"Demo keyboard\",\"price\":\"49.90\",\"categoryId\":\"$ORDERFLOW_CATEGORY_ID\"}" \
  "$ORDERFLOW_AUTH_URL/api/admin/products"
curl --get --fail-with-body --data-urlencode 'q=KEYBOARD' \
  --data-urlencode "categoryId=$ORDERFLOW_CATEGORY_ID" --data-urlencode 'pageSize=20' \
  "$ORDERFLOW_AUTH_URL/api/products"
```

4. Save returned product ID/version, PUT a new name/price/categoryId/isActive with expectedVersion=1; expect 200/version=2. Repeat old version: 409. POST its /archive with expectedVersion=2: public detail becomes 404, admin detail remains 200. Recreate the same SKU: 409, even archived. Archive/restore the category and verify child visibility described above. A Customer cookie must get 403 on admin paths; omitting Admin CSRF must get 400. Include onHand or sku in a PUT: 400. Run only against sample data you intentionally create.
5. Verify tests with Docker running (or optional private ORDERFLOW_TEST_POSTGRES); see [testing guide](testing.md):

```bash
dotnet test OrderFlow.slnx -c Release --no-build --no-restore
# Focused SQL/HTTP catalog tests:
dotnet test tests/OrderFlow.IntegrationTests -c Release --no-build --no-restore \
  --filter 'FullyQualifiedName~OrderFlow.IntegrationTests.Catalog'
```

Use the same --artifacts-path as your build when using an external output path. Current verification evidence/limits are in [implementation status](implementation-status.md). Tests use real PostgreSQL and production Identity cookie/CSRF, independent contexts and deterministic race gates; no EF InMemory/auth bypass. Order FK/snapshot behavior, actual checkout eligibility, client cache invalidation and large-data performance remain later integration work.

Inventory 08 initializes a zero balance and System opening movement atomically for each product; apply 20261104083112_AddInventory as well.
